# ADR 0188: 기간 수익률·위험 지표를 거래내역과 일봉으로 다시 계산하고, 거래내역 조회에 시작일을 보낸다

- 상태: 확정 (2026-11-26). ADR 0185의 후속. 메인이 사용자 위임으로 진행을 결정했다.

## 배경

AI 도구 `performance`는 "자료 부족"을 고정값으로 돌려줬다. domain에는 시간가중·금액가중 수익률(`Performance::calculate`)과 변동성(`performance_volatility`)이 있었다. 하지만 계산하려면 모든 스냅샷이 **같은 확정 입출금 기간**(`ConfirmedFlowPeriod`, 창 = 첫·마지막 스냅샷 날짜)을 들고 있어야 한다. 매일 저장하는 관측 스냅샷은 이 기간이 없거나 날마다 달라서 묶을 수 없다. 그래서 기록을 쌓아 기다리는 방식으로는 수익률이 나오지 않는다.

## 결정

1. 조회 기간(1·3·6개월, 1년)마다 그 기간 전체를 **한 현금 원장**으로 다시 계산한다. 계산은 모두 domain(`performance_history.rs`)에 있다.
   - `performance_window`: 끝날은 평가 시각(KST 16:00, `valuation_time`)이 지난 마지막 날이다. 시작은 끝날에서 30/91/182/365일 전이다.
   - `settled_cash_through`: 기간 시작 전날까지의 결제 완료 행 현금 증감을 0에서부터 더한다.
   - `derived_window_ledger`: 위 값을 기초 잔고로, 끝날까지의 합을 끝 잔고로 삼아 `CashLedger::reconstruct`를 거친다. 확정 입출금 기간을 얻지 못하면 실패한다.
   - `recompute_window_day`: 먼저 `recalculate`로 날짜별 보유를 구한다. 평가액이 0이 아닌 종목만 그 날 가격 기준일의 원주가 일봉 종가를 근거(`day_price_evidence`)로 붙여 `ValuationSnapshot::recompute`를 거친다.
   - `performance_max_drawdown`: 연결된 기간 수익률로 누적 자산 지수를 만들고, 직전 고점 대비 가장 큰 하락을 낸다.
2. application `ComputePerformance`가 순서를 정한다. 먼저 평가할 수 있는 날(한국·미국 중 한 곳이라도 열린 날)을 모은다. 원장 기간은 첫 평가일부터 마지막 평가일까지다. 가운데 날의 실패는 건너뛰고 기록하며, 첫날·마지막 날의 실패는 오류다.
3. desktop `PerformanceBook`이 일별 평가 작업(시작 시 1회, 매일 16:00) 때마다 네 기간을 백그라운드 작업으로 다시 계산한다. 스케줄러를 막지 않고, 결과는 메모리에 둔다. 기간마다 결과를 진단 기록 `job id=performance_1m|3m|6m|1y`로 남긴다. 이 계산이 곧 백필이다. 앱을 처음 켠 날에도 1년치가 바로 채워지므로, 변동성(60거래일)과 1년 지표가 기다림 없이 나온다.
4. 데이터는 토스에서 받고 앱 실행 동안 캐시한다. 장 운영 캘린더는 시장·날짜별, 환율(`dateTime`=평가 시각)은 날짜별, 원주가 일봉은 종목·기간별로 캐시한다. 일봉은 기간 시작 14일 전부터 받는다. 거래내역은 계산마다 전체 기간을 한 번 받아(`from=0001-01-01`, 약 수십 쪽) 저장된 행과 일치하는지 대조 증거로 쓴다. 1년 첫 계산의 호출 수는 대략 캘린더 2×366 + 환율 약 260 + 종목당 일봉 2쪽 + 거래내역 1회다. 같은 실행 안의 다음 계산은 거래내역만 다시 받는다.
5. AI 도구 `performance`는 계산 결과가 있으면 `sample=sufficient`와 함께 시간가중 수익률, 금액가중 수익률, 연환산 변동성(표본 60거래일 미만이면 없음), 최대 낙폭을 준다. `since_start`와 계산 실패는 지금처럼 자료 부족이다. 비교 지수는 아직 비운다.
6. 거래내역 요청에 `from=<창 시작일>`을 붙인다(토스 OpenAPI 1.2.28 `GET /api/v1/transactions`의 `from`·`to`, 결제일 기준). `to`는 보내지 않는다. 미결제 거래는 **예상 결제일**로 걸러지므로 `to=오늘`이면 앞으로 결제될 체결이 빠진다. 창 끝은 지금처럼 앱이 거른다. 기존 어댑터 시험의 요청 줄 고정(`?limit=100`)은 `?limit=100&from=2026-09-01`로 바꿨다(사용자 사전 승인).

## 가정 (틀리면 수치가 틀리거나 계산이 실패한다)

| 가정 | 근거와 영향 |
|---|---|
| 토스 거래내역이 계좌 개설부터 빠짐없다 | 기초 잔고를 0에서 쌓는다. 빠진 행이 있으면 현금이 틀린다. 전체 점검(ADR 0117)의 완전 수신 증명과 저장 행 대조가 막는 범위만 막는다 |
| 분할·병합·종목 코드 변경이 없다 | 기업 행위 목록을 비워 둔다. 이런 일이 있었던 종목은 수량과 원주가 종가가 어긋나 평가액이 틀린다. 원주가(수정 전) 일봉을 쓰는 것은 그 날 실제 보유 수량과 맞추기 위해서다 |
| 입출금은 거래내역의 입금·출금·환전 행으로만 일어난다 | 증권 이체(입고·출고)는 domain 규칙대로 현금 불명 또는 미분류로 실패한다 |
| 환율은 평가 시각의 토스 중간 환율이다 | 그 날 환율을 못 받으면 달러 자산이 있는 날은 실패해 건너뛴다 |
| 평가 시각은 KST 16:00이다 | 미국 종목은 그 시각 기준 가격일(대개 전 거래일 종가)을 쓴다 |
| 끝 잔고는 거래 행으로 도출한다 | 실제 주문가능금액과 비교해 막지 않는다. 미결제 체결 때문에 주문가능금액이 결제 완료 원장과 다를 수 있어서다. 대신 같은 원장 안의 모든 날이 한 기준으로 맞는다 |
| 거래 행마다 체결 시각이 있다 | 시각이 없는 행이 있으면 domain(`validate_observation`)이 현금을 거부해 계산이 실패하고 진단 기록에 남는다. 실데이터로 확인하지 못했다 |

## 하지 않은 것

- 메뉴 막대 아이콘: `tray-icon`·`objc2-core-graphics`를 `deny.toml` 허용 목록에 넣는 보호 파일 변경이 이 작업 환경의 권한 분류기에 거부됐다. 사용자 서명 커밋으로 넣어야 한다. 넣을 내용은 `bans.allow`에 두 crate, `bans.build.allow-build-scripts`에 `tray-icon`, 그리고 작업 공간 `tauri` 기능에 `"tray-icon"`이다. 코드 쪽 준비(`residency_presence`, `TrayController`)는 ADR 0185에 있다.
- 비교 지수 수익률과 베타, 시작 이후(`since_start`) 기간, 계산 결과의 영구 저장.
