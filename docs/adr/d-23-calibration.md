## 집계 규칙과 변경 이유

“기간이 겹치지 않는 추정만 센다”는 서로 겹치지 않는 추정의 집합이다. 최초 연결 성분 방식은 매일 또는 매주 추정하는 종목의 전체 이력을 한 건으로 합치고, 중간 구간이 뒤늦게 들어오면 건수가 줄어드는 문제가 있어 폐기한다.

같은 모델·기간 조합 안에서 종목별로 시작 시각 오름차순으로 훑는다. 첫 추정은 세고, 마지막으로 센 추정의 만기보다 엄격하게 뒤에 시작하는 추정만 센다. 제외한 추정의 만기는 다음 선택에 영향을 주지 않는다. 같은 시작은 긴 만기 → 실패 → 낮은 확률 → 추정 식별자 오름차순으로 정한다. 비교하는 시각과 확률은 아래 정규 표현이다.

뒤에 추가한다는 것은 새 추정의 시작이 기존 입력의 모든 시작보다 엄격히 뒤라는 뜻이다. 이 조건에서는 기존에 센 추정과 건수가 줄지 않는다. 같은 시작의 동률 후보나 과거 시작의 추정이 나중에 판정되어 들어오는 경우에는 선택 결과·건수·구간별 적중이 바뀔 수 있다. 집계는 입력 집합의 결정적 스냅샷이며 판정 기록 자체를 수정하지 않는다. A-15는 기록을 지우거나 판정을 바꾸지 않고 새 결과를 더한 뒤 집계를 다시 만든다.

종목 30개에 7일마다 28일짜리 추정을 52회 만드는 예는 1,560건 중 330건을 센다. 닫힌 끝점에서는 각 종목의 0·5·10·…·50번째 추정, 즉 11건이 선택된다. A[0,2], A[4,6]에 A[2,4]를 더해도 앞의 두 추정은 남는다. 시간 축은 원래 전체 과제 구간의 절대 시각이다. 거래일 H를 벽시계 길이로 임의 환산하거나 목표·손절 조기 도달 시점까지 구간을 줄이지 않는다.

## 입력·정규화·모순 처리

CalibrationEstimate는 CalibrationEstimateId, InstrumentId, CalibrationKey(모델 식별과 Horizon), 원래 과제 구간, AiProbability를 담는다. CalibrationFact는 이 추정과 Hit/Miss만 묶는다. 추정 시각은 구간 시작, 만기는 원래 과제의 끝이다. D-27이 EstimateOutcome을 판정해 이 사실을 만들거나 대체한다. Hit는 Hit, StoppedOut·Expired는 Miss로 대응한다. 판정 완료 여부·출처 인증과 실제 거래일 만기 계산은 D-27·D-21·A-15 책임이다.

추정 식별자는 ADR 0022의 불투명 식별자 관례에 맞춘 ASCII 표시 문자 1~64바이트다. 같은 조합 안의 같은 ID는 같은 추정을 뜻한다. ID가 같고 모든 사실이 같으면 한 번으로 친다. 결과가 다르거나 종목·구간·확률 등 추정 내용이 달라도 ConflictingEstimate로 전체 입력을 거부한다. 오류에는 입력값이 없다. 실제 ID 발급·영속 유일성은 S·A 작업 책임이다.

CalibrationInstant는 Timestamp의 UTC 초와 나노초만 보존한다. CalibrationInterval은 이 두 정규 시점으로 원래 구간을 보존한다. 오프셋 표현은 입력에서 제거하므로 같은 순간은 정렬·선택·Debug 결과까지 같다. 유효한 기존 TimeInterval에서만 만들어 구간 불변 조건을 재사용한다. 불가능한 재파싱 실패 분기를 만들지 않는다.

판정 사실과 calibrate는 모두 일반 Probability 대신 ADR 0027의 AiProbability를 받는다. 이 타입은 1~99 정수 퍼센트 파서만 제공하고 내부 Decimal 스케일을 항상 2로 만든다. 따라서 0.6·0.600 같은 임의 스케일의 일반 Probability는 입력될 수 없다. AI 경계의 정수 60으로 제출한 값은 항상 같은 0.60이다. 시각 표현 변형은 속성 생성기에 넣고, 확률 스케일 문제는 이 입력 타입의 단일 정규형과 일반 Probability 입력의 컴파일 거부로 검증한다. 원래 정수 퍼센트 입력에 소수 문자열을 허용하지 않는다.

모델 식별은 제공자·모델 이름·모델 버전을 별도 ModelIdentityPart로 보존한다. 각 부분은 ASCII 표시 문자 1~64바이트이며 정규화하지 않는다. 다른 제공자·이름·버전·Horizon은 다른 조합이다. 실제 버전을 모르는 별칭을 고정 버전으로 꾸미지 않는다. 프롬프트 비교 수·버전·추론 강도는 D-17과 실행 기록 책임이다.

## 조합별 입력과 자원 제한

Calibration::try_new는 조합 키 하나와 그 조합의 판정 사실만 받는다. 다른 조합이 섞이면 MismatchedCombination이다. 조합 하나당 입력 상한은 65,536건이다. 종목 200개 × 주 1회 × 연 52주 × 5년 = 52,000건을 수용하고 약 26% 여유를 둔 유한 자원 초안이다. 이는 제품의 보관 기간이 아니다. 다른 조합은 별도 Calibration으로 만들므로 모델 교체나 기간 추가가 기존 조합의 상한을 소모하지 않는다.

상한은 복사·정렬 전 입력 행 수에 적용한다. 완전 중복이라도 입력 자원은 사용하므로 65,537개를 받으면 TooManyFacts로 전체를 거부한다. 조용히 자르지 않는다. S·A-15는 이 상한을 넘을 때 자른 위치에 따라 통계가 달라지는 임의 창을 만들면 안 된다. 더 큰 실제 운용이 필요하면 상한과 이력 집계 설계를 함께 재검토한다.

## 결과 타입과 후속 소비자

CalibratedProbability는 InsufficientSamples(ConservativeCalibration)와 EligibleBeforeE91(EligibleCalibration)의 닫힌 두 변형이다. 공통 probability·evidence 접근자는 없다. 값을 읽으려면 match로 분기한 뒤 해당 봉인 payload의 evidence를 읽는다. 두 payload는 서로 다른 비공개 필드 타입이며 공개 생성자·Default·From·역직렬화·가변 접근자가 없다. 보수 운용 payload를 보정 가능 변형으로 다시 포장할 수 없다. Calibration::calibrate만 AI 추정에서 결과를 만든다.

각 변형은 CalibrationEvidence에 원래 확률, 요청 조합, 그 조합의 판정 수를 담는다. 0~29건은 InsufficientSamples, 30건부터 EligibleBeforeE91다. 요청 조합이 없거나 적중표가 비어 있으면 항상 표본 부족이다. 두 경우 모두 E-91 전에는 원래 AI 확률을 정확히 반환한다. EligibleBeforeE91는 이미 보정됐다는 뜻이 아니다.

D-24는 이 결과만 받고 두 변형을 분기해야 한다. D-22·D-25는 표본 부족에서 여유분 15%p와 작은 매수 비중을 강제하고 D-17은 판정 보류로 표시한다. 이번 작업은 이 후속 유스케이스·주문·화면을 구현하지 않는다. 30건은 실력 증명의 기준이 아니다. E-91은 실제 보정 방법과 Brier 비교를 도입할 후속 작업이다.

선택 사실 접근자로 D-17이 같은 표본을 사용할 수 있다. 건수·적중 수는 정수 CalibrationCount이며, 빈 구간의 적중률은 None이다. 그 밖에는 ADR 0029의 RatioQuotient(정확/근사)를 보존한다. 구간별 적중률은 표시용이며 보정 함수로 대체 사용하지 않는다.

## 검증

새 계약 테스트를 먼저 작성해 이전 API에서 컴파일 실패를 확인한 뒤 구현했다. 속성 테스트 네 개는 각각 4,096회이며 성공·실패, 1~99 확률, 여러 종목·시작·만기·오프셋을 생성한다. 뒤에 추가할 때 기존 선택 보존, 선택끼리 비겹침, 입력 순서 및 정규 표현 불변, 독립적인 반복 최소 선택·겹침 제거 기준과의 일치를 따로 검사한다. 주 1회 28일 1년 예의 330건, 동률, 뒤늦은 과거 입력, 중복·모순, 29/30·빈 조합, 52,000·65,536·65,537건도 검사한다.

프로젝트 신뢰·Codex 훅 신뢰의 실제 런타임 적용 증거는 확보하지 못했으며 전체 검사와 설치한 Git 훅 결과를 확인한다. 새 의존성·검사 끄기·master의 기존 테스트 변경은 없다. 이번 지시대로 cargo-mutants와 just mutants-diff는 실행하지 않고 분기 제거 손 변형으로 검출을 확인한다. 최종 전체 검사·손 변형 결과와 SHA는 구현자 보고서에 기록한다.

수정 검증: 분기 제거 13개와 끝점·종목 분리·역순 정렬·동률 비교 제거 6개, 총 19개 손 변형을 각각 주입했다. 전부 컴파일된 뒤 nextest의 실제 테스트 실패(종료 100)로 검출됐고, 원본 복구 후 표적 12개가 다시 통과했다. 외부 rustc 소비자에서는 명시적인 두 변형 match만 성공하고 공통 probability 접근, 일반 Probability를 calibrate·추정 입력에 전달, 보수 payload를 보정 가능 변형으로 재포장, 보정 가능 payload 직접 생성은 각각 컴파일 거부를 확인했다. 이는 현재 API의 수동 검증이며 영속 compile-fail 회귀는 후속 하네스 범위다.
