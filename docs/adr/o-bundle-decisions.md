# O 묶음 경량 결정 기록 (ADR 0173)

문서가 세부 값을 정하지 않은 선택지를 가장 안전한 쪽(주문이 나가지 않는 쪽)으로 정한 기록이다.

| 작업 | 정한 것 | 다른 선택지 |
|---|---|---|
| O-03 | `UserApproval`과 `ApprovedOrder`가 `domain::PendingOrderConfirmation`을 소유해 `Proposal<Validated>`와 사용자가 본 `OrderSummary`가 분리되지 않게 한다. `PendingOrderConfirmation`에는 분해 없는 읽기 접근자만 추가하고 `into_execution_parts`는 `pub(crate)`를 유지한다. `OrderOutcome::Unknown`은 `Maintenance`가 아닐 때만 원본 `ApprovedOrder`와 최초 전송 시각을 봉인한 `UnknownOrderRetry`를 반환하고, `Accepted`·`Rejected`·`Maintenance`는 `ApprovedOrder`를 즉시 소멸시킨다. | `UserApproval`이 `ExecutionToken`과 `OrderSummary`를 별도 필드로 분해해 소유하는 방식, 또는 `OrderOutcome::Unknown`에서 원시 주문 재구성 허용 |
| O-01 | 장 시간 게이트에서 미국 금액 주문·소수 수량 매도는 정규장 시작부터 정규장 종료 1시간 전 미만(`[start, end - 1h)`)만 통과시키고, 일반 시장가 주문도 보수적으로 정규장(`RegularMarket`)만 통과시키며, 지정가 주문은 개장 세션 전체를 허용한다. 매수 가능 금액 검사는 유효한 수수료율 사실이 있으면 추정 수수료를 더한 금액과 비교하고, 매도 수량 검사는 매도가능수량 사실과 보유 수량 둘 다 이내여야 통과시킨다. 국내 주문은 가격 제한 사실이 없으면 `Unknown`으로 거부한다. | 시장가 주문을 프리·애프터마켓에서도 허용하거나, 수수료를 제외한 원금만으로 매수가능금액을 비교하는 방식 |
| O-22 | 전체 시간당 주문 건수 상한(ORD-6) 기본값을 **롤링 1시간(3600초)당 10건**(설정 허용 범위 1~30건)으로 정한다(토스 어뷰징 예 "수십 분 내 수백 건"보다 충분히 낮음). 미래 시각 전송 기록(시계 역행)이 있으면 보수적으로 거부(`ClockRollback`)한다. | 정시 단위 고정 창(버스트 허용) 또는 더 높은 상한(50~100건) |
| O-04 | 거절한 제안의 재요청 제한(쿨다운) 기본값을 **60초**(설정 허용 범위 1~3600초)로 정한다. 확인 창 동시성 제한은 `ApprovalGuard`의 RAII `DialogLease`로 강제해 호출 종료·패닉 시에도 1건 제약을 안전하게 해제한다. `ProposalExpired` 이벤트는 `ProposalId`당 최초 1회만 발행한다. | 더 짧은 쿨다운(5~15초) 또는 전역 쿨다운 |
| T-16 | 읽기 쪽 HTTP crate는 따로 두지 않는다. `broker-toss`는 `TossEndpoint`의 기준 주소·모드만 공개하고, `broker-toss-trade`가 리디렉트·프록시 없음, 5초/30초, HTTP/1.1, 운영 `https_only`, 루프백 이름 해석 거부로 자체 `reqwest` 클라이언트를 만들어 `POST /api/v1/orders`만 보낸다. 토큰은 `TradeAccessToken`(구현: `broker-toss::TokenManager`)에서 받고, 토큰을 못 받으면 연결 없이 `AuthenticationRequired` 거절, 401은 재발급·재전송 없이 거절, 429는 `RateLimited` 거절(재전송 없음), 409 `request-in-progress`·5xx·전송 오류·응답 해석 실패·`clientOrderId` 불일치는 결과 모름, 5xx `maintenance`는 재시도 금지 결과 모름, 문서에 없는 4xx 코드는 `OtherRejected`. `timeInForce`는 항상 `DAY`, `confirmHighValueOrder`는 항상 명시한다. | 읽기 전용 HTTP crate 분리, 401에서 토큰 재발급 후 같은 키로 재전송, 429 대기 후 재전송 |
| O-05 | 이벤트로만 알 수 있는 추정 제출·신호 발생·넘기기는 `AuditEventRecorder`(이벤트 버스 구독자)가 시각을 붙여 `AuditEventSink`에 넣고, 조립 루트의 `AuditEventQueue`가 감사 로그에 차례로 붙인다(실패하면 그 항목을 큐 앞에 되돌려 다음에 다시 붙인다). 위험 설정 변경은 `ChangeRiskSettings::with_audit`가 확인 창 결과마다 `RiskChangeConfirmationRecorded`, 저장 뒤 바뀐 항목마다 `RiskSettingsChanged`를 1건씩 남긴다. 기존 `new`는 감사 없이 남겨 기존 테스트를 바꾸지 않는다. 승인 요청·본인 확인·검증·전송 전·응답 기록은 기존 `approval-command`·`order_gate` 경로를 그대로 쓴다. | 각 유스케이스 생성자에 감사 포트를 추가(기존 테스트 변경 필요), 구독자에서 감사 로그를 동기 블로킹으로 직접 호출 |
| O-06 | 주문 기능 스위치는 기존 `RiskSettings::orders`(저장 없음 = 꺼짐)와 `ChangeRiskSettings`의 `EnableOrders` 확인 창을 그대로 쓴다. 카드 버튼 판단은 `domain::order_button_state`(스위치 → 장 → 제안 순으로 숨김 이유 하나)와 `application::ReadOrderButton`이 하고, 장 상태 `Unknown`은 닫힘과 같게 숨긴다. 신호 카드 화면이 아직 없어 TS 쪽 표시는 카드 작업에서 이 값을 받는다. | 장 상태 `Unknown`에서 버튼 표시, 버튼 판단을 TS에서 |
| O-08 | `approval-command::service::ApprovalService`가 승인 경로의 포트를 `Arc`로 소유하고 확인 창 가드·결과 모름 보관함을 한 벌 둔다. src-tauri는 `OrderApprovalHandler`(dyn) 하나만 `OrderApprovalRuntime` 상태로 들고, `request_order_approval`은 `{ request: { proposal_id } }`만 받는다(`deny_unknown_fields`). 런타임이 등록되지 않으면(현재 제품 조립) 아무 포트도 부르지 않고 `unavailable`을 돌려준다. 실제 저장소·`broker-toss-trade` 조립은 store-sqlite가 승인 경로 포트를 구현한 뒤 붙인다. 응답 사유 문자열은 주문 경로 검사(`orders` 글자)와 겹치지 않게 `switch-off`로 쓴다. | `Ports`/`PortTypes`에 승인 포트 9개를 더해 build_app 안에서 조립, 제품에서 Unavailable 포트로 승인 서비스를 항상 조립 |
| O-25 | 토스 주문에는 `clientOrderId`가 없으므로 접수된 전송은 주문번호로, 결과 모름 전송은 같은 종목·방향·수량이 준비 시각 1분 전~10분 뒤에 있는지로 대조한다. 불일치는 접수됐는데 없음·내용 다름·결과 모름인데 없음 세 가지이고, 토스 조회가 불완전하면(미체결 또는 종료 주문 증명이 불완전) "없음"은 판정하지 않고 상태를 `Incomplete`로 둔다. 앱 기록에 없는 토스 주문(사용자가 토스 앱에서 낸 주문)은 불일치로 보지 않는다. 고급 > 상태 화면이 아직 없어 코어 유스케이스(`ReconcileSubmittedOrders`, 원장 포트 `SubmissionLedger`)까지만 둔다. | 앱 기록에 없는 토스 주문도 불일치로 표시, 불완전 조회에서도 없음 판정 |
| O-11 | 범위표대로 코어만 한다. 네 상태는 미체결·부분 체결·체결·종료(취소·거부·정정됨)이고, 열린 상태라도 체결 수량이 있으면 부분 체결로 본다. `TrackSubmittedOrders`는 마지막으로 본 상태가 체결·종료인 주문은 다시 조회하지 않고, 처음 체결·종료가 된 때만 `OrderFilled`·`OrderCancelled`를 낸다. 조회 실패는 마지막 상태를 그대로 돌려준다. 주문 직후 보유 동기화는 기존 `OrderSubmitted` 구독(U-08)을 쓴다. 주문 내역 보조 화면은 프런트 묶음에서 `OrderHistoryRow`를 받는다. | 정정됨(`Replaced`)을 별도 상태로, 조회 실패를 오류로 끊기 |
| O-26 | 범위표대로 코어만 한다. `trade_cost_display`는 주문이 체결(`Filled`) 상태이고, 같은 종목·시장·방향의 결제 완료·취소 아님 거래내역이 주문 시각 이후에 있으며 그 수량 합이 체결 수량과 같을 때만 `commission`·`tax`·`netAmount` 합으로 바꾼다. 하나라도 어긋나면(부분 체결, 미결제, 수량 부족, 금액 합 넘침) 추정값을 그대로 둔다. 녹화 응답 시험은 기존 T-15 주문 상세 녹화와 새 거래내역 녹화로 broker-toss 경계에서 돌린다. | 부분 체결분도 바로 확정 표시, 수량이 달라도 가장 가까운 거래로 확정 |
| O-07·O-09 | 범위표대로 코어만 한다. `platform-macos::MacOsPresence`가 요약 창 포트(`OrderDialogBackend`, 실제는 `rfd`)를 먼저 띄우고, 확인일 때만 본인 확인 포트(`DeviceOwnerAuthBackend`, 실제는 `LAContext`를 `spawn_blocking`에서 재사용 0초로)를 부른다. 요약 창 문구는 코어 `OrderSummary`의 값만 쓰고(수수료는 "추정"), 고액(1억 원의 80% 이상 또는 환산 불가) 확인 문장을 같은 창에 넣으며, 최종 확인 고지 문구(R-13 Q7)를 붙인다. 본인 확인 이유 문자열은 "종목 수량 방향 주문"이다. 창은 주문·위험 설정 확인을 합쳐 한 번에 하나만 띄우고(원자 슬롯), 이미 떠 있으면 새 창 없이 `Unavailable`. 실제 `rfd`·`objc2-local-authentication` 연결과 `unsafe` 처리 ADR은 macOS 호출이 필요한 실기 작업으로 미룬다. 기존 `MacOsRiskDialogPresence`는 기존 시험을 건드리지 않으려고 그대로 둔다. | 본인 확인을 먼저 부르고 요약 창을 나중에, 고액 확인을 별도 창으로 |
