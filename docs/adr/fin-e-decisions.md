# ADR: fin-e 묶음 결정 표

- 상태: 확정 (ADR 0173 경량 절차, 2026-11-25)

| 작업 | 정한 것 | 다른 선택지 |
|---|---|---|
| 뉴스 수집 워커 연결 | application `CollectFeed`가 피드 한 번의 수집(`new_items` → 뉴스는 `NewsRepository`, 공시는 `DisclosureRepository`에 저장 → 공시마다 `DisclosureArrived`, 끝나면 `CollectionFinished` → `RecordSourceStatus`로 소스 상태 기록)을 맡고 다음 커서를 돌려줌. 소스 실패·키 없음·자료 없음은 커서를 그대로 두고 상태만 기록, 저장 실패는 커서를 넘기지 않고 오류로 끝냄. src-tauri `FeedCollectorWorker`가 30초 틱마다 `PlanCollectionSchedule`(N-11 표, 장 상태는 `MarketInfo`, 실패하면 장 밖 표)로 각 피드의 주기(`collection_due`)를 판정해 돌림. 커서·마지막 시도 시각은 메모리에만 두어 앱 시작 때 처음부터(`FeedCursor::Start`) 수집. KIND는 첫 회만 하루치 따라잡기 창(`StartupCatchUp`), 이후 정규 창. 조립 루트는 키가 필요 없는 언론사·거시 RSS 6종과 KIND 공시만 등록(DART·SEC·Google 뉴스·Yahoo는 키·연락처·종목 목록이 필요해 등록하지 않음). DART 키는 없음으로 고정. DB가 열리지 않았으면 요청을 보내지 않음. 피드 타입이 제각각이라 `SharedFeed`(형 지움)로 묶고 `Ports.news_feeds`는 그대로 둠 | 커서를 DB에 저장(새 표 필요), 모든 소스 등록, 스케줄러 작업으로 등록(작업 ID 추가 필요) |
| J-03·J-04·J-05 연결 | application `HoldingsBriefingContext`가 저장된 계좌들의 최근 보유(완전·부분 동기화만)에서 종목을 겹치지 않게 최대 20개 모으고, 종목마다 저장된 뉴스 최대 5건을 근거(관측 시각은 실행 시각)로 붙임. `code_facts`(마감 리뷰의 변동 분해 수치)는 domain 계산 유스케이스가 없어 비워 둠. 앱은 `AppStoredJobs`가 `BriefingPort`를 구현해 실행 때 `Ports`의 AI 제공자·보유·뉴스·시계·이벤트를 읽고 브리핑 저장은 `SqliteRepositories`로 함. 아침·마감·미국장 전 세 작업을 공유 DB가 있을 때 등록. AI 큐가 `DisabledAiJobQueue`(예산 도달)이므로 AI 큐·제공자가 연결되기 전에는 실제로 돌지 않음 | 보유 대신 관심 종목, 마감 리뷰 변동 분해를 앱에서 계산(금지: 계산은 domain) |
| E-91 | 보정 방법은 ADR 0177: 조합 전체 판정의 선형 재보정 뒤 기준 확률 p₀ 쪽으로 (n·f(p) + 30·p₀)/(n + 30) 축소, 30건 미만은 원래 값. Brier 전후는 판정마다 순차로 계산해 판정 보고와 J-12 집계에 남김. E-90 자료로 재조정 필요 | 구간별 적중 축소, 로지스틱·등위 회귀, 판정에 p₀ 저장 |
| E-92 | 건너뜀: E-90 실측 자료가 필요(지시) | - |
| J-11 연결 | `AppStoredJobs`가 `DailyValuationPort`를 구현해 16:00 작업에서 `MarketInfo`의 국내·미국 장 운영 정보로 `SnapshotCalendar`를 만들고 계좌마다 `TakeValuationSnapshot`(보유는 `Ports`, 시세·마감 근거·평가 저장은 `SqliteRepositories`)을 돌림. 장 운영 정보를 못 읽으면(토스 키 없음) 기록 없이 작업 실패. 빠진 날 재계산은 `ValuationCalendarSource`·`ValuationDayInputSource`·`ValuationDaySuccessSource` 구현이 없어 `missing_days`가 빈 목록(재계산 0회) | 빠진 날을 가짜 입력으로 채움 |
| J-12 | 건너뜀: 판정 기간 전체의 장 운영 일정 이력(`MarketInfo`는 오늘 기준 일정만 줌)과 기업 행위 자료 원천이 포트에 없음. 이대로 연결하면 `ResolveEstimates`가 자료 부족을 `record_unavailable`로 영구 기록해 미결 추정을 잃음. `SqliteRepositories`의 판정 저장소 위임과 Brier 집계(E-91)는 준비됨 | 오늘 일정·빈 기업 행위로 판정(오판정 위험) |
| J-10 | 건너뜀: `JobScheduleSettingsRepository`·`JobRecordSink` 저장에 새 표(마이그레이션 0021)가 필요하고 `JobRecordSink`가 동기 트레이트라 앱 쪽 비동기 쓰기 큐 설계가 따로 필요. 설정 화면 명령도 없음(front 묶음) | settings 표 CHECK 확장(마이그레이션 필요) |
| 수집 격리 거부 흔들림 | 원인: 격리 거부 이벤트가 채널로 먼저 나가 `ClaudeWebCollectionRunner::collect`가 곧바로 `Rejected`를 돌려주고, 자식 정리(stdin 닫기 → 종료 → 회수)는 읽기 스레드에서 뒤이어 일어남. 시험은 가짜 CLI가 종료 때 쓰는 호출 기록을 회수 전에 읽어 빈 목록을 볼 수 있었음(부하 4코어 점유에서 10회×15번 중 2번 실패). 수정: 거부 뒤 스트림 끝(회수 뒤 보내는 End)까지 비운 다음 `Rejected`를 돌려줌. 같은 부하에서 0/15. 수집 호출이 끝나면 자식 프로세스가 남지 않는 성질도 함께 생김 | 시험에서 기록 파일을 될 때까지 기다림(제품의 프로세스 수명 문제를 가림), 회수 유예 250ms 늘리기 |
| J-06 | 다시 확인: J-02(`UpdateThesis` MCP 도구)와 E-05(`RunEstimateCycle`, `SingleEstimateRunner` 포트)는 master에 있으나 AI 분석 실행을 실제로 띄우는 구현이 없음. application `RunIntradayReview`가 사건(긴급 공시 접수 번호·가격 급변·뉴스 급증 종목)마다 `RunPurpose::IntradayMonitoring` 분석 실행 하나를 띄움. 고정 지시문은 get_thesis/update_thesis로 바뀐 주장만 고치고, 코드가 만든 추정 과제가 있으면 get_estimate_task/submit_estimate로 확률만 내라고 함. 사건 식별자는 `<subject>` 안 값으로만 넣음. 결과 쓰기는 MCP 도구가 함(앱은 실행·소진만). 격리 통과 뒤 정상 종료만 완료로 보고 거부·도구 없음·한도·제공자 실패는 작업 실패(같은 사건 다음 트리거에서 재시도). 앱은 늦게 묶는 `IntradayWatchSlot`을 이벤트 버스에 구독시키고 스케줄러를 만든 뒤 `IntradayWatchSubscriber`를 묶음. 실행 전 AI 큐 허가를 받음 | 앱이 추정 과제를 직접 발급(E-04 범위), 사건마다 별도 작업 ID |
