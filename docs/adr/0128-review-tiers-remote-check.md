# ADR 0128: H-52 리뷰 회차 등급과 전체 검사의 원격 실행

- 상태: 확정 (2026-11-18)

## 배경

2026-11-17 사용자 결정은 병합 때 중복 전체 검사를 줄이고, 작업의 위험도에 따라 리뷰 회차를 다르게 하며, 작업 브랜치의 전체 검사를 원격에서 실행하는 것이다. 여러 작은 작업은 한 브리프로 묶을 수 있다. 컴파일 결과 공유는 H-51이다.

## 결정

| 리뷰 등급 | 대상 | 독립 리뷰·비판 상한 |
|---|---|---|
| 3 | 하네스, 보안·권한, 금액·수량·환율 계산, 주문 | 3회 |
| 2 | 일반 유스케이스, 저장소, 외부 연동 | 2회 |
| 1 | 문서, 기계적 연결, 화면 배치·표시 | 1회 |

메인이 브리프에 등급을 쓰고 구현자는 계산·보안 범위를 발견하면 올릴 수 있다. 브리프에 등급이 없으면 3이다. 마지막 회차에서 실행으로 재현한 차단·중요 지적은 수정하고 추가 독립 리뷰 없이 수정 범위와 회귀·변이 결과를 기록해 메인이 평가한다. 새 리뷰 기록은 측정 표에 등급을 한 번 적는다. 도입 전 기준 `d235aaf8d3f3a6387e0a20aede316cc5b7d0edbf`에 있던 기록이 같은 경로에 같은 바이트로 남아 있으면 등급이 없어도 통과한다. 바뀐 기록이나 새 기록은 진행 표에 연결되기 전에도 등급을 요구한다. 기준 Git 객체를 읽을 수 없으면 예외를 주지 않는다.

기계 검사는 등급의 유효값과 기록 안의 회차 상한·정합성을 확인하지만, CI에 메인의 신뢰된 브리프가 없으므로 기록 등급이 브리프보다 낮은지나 위험도 분류가 적절한지 증명하지 못한다. 메인이 브리프와 실제 범위를 기록에 대조한다. 사용자가 리뷰 생략을 결정한 새 기록은 측정 회차를 0으로 두고 리뷰 절과 생략 절을 동시에 두지 않는다. 그때 커밋 표는 구현 이력이다.

| 검사 | 위치와 범위 |
|---|---|
| 커밋 | 기존 `check-fast`. 하네스·설정·문서 변경 등은 기존 규칙대로 전체 검사로 승격한다 |
| 푸시 | 기존 로컬 `check-full` 유지. 허용된 병합 생략 외에 검사를 줄이지 않는다는 지시에 따른다 |
| 부하 제한 | `justfile`이 외부 `NEXTEST_TEST_THREADS`를 지우므로 nextest 기본 프로필을 동시 테스트 4개로 고정하고 설정 검사에 정확한 값을 등록한다. Cargo 빌드 작업은 실행 환경에서 4개로 제한한다 |
| 원격 Linux | 모든 브랜치 push에서 기존 플랫폼 중립 검사, 네트워크 차단 테스트와 컨테이너 시각 회귀 |
| 원격 macOS | 모든 브랜치 push에서 `just check`와 `mutants-diff`. `check`의 전체 nextest와 커버리지를 포함한다 |
| Tauri 실제 빌드·WKWebView | 현재 `just check`의 별도 실제 앱 빌드나 WKWebView 실측으로 주장하지 않는다. 해당 작업의 환경과 증거가 필요하다 |

`just remote-check <sha>`는 GitHub API에서 해당 SHA의 최신 push 실행을 직접 읽고 `ci.yml`의 Linux·해당 브랜치의 macOS 작업과 `signatures.yml`의 서명 작업이 같은 실행 회차에서 완료·성공했는지 확인한다. 각 작업의 검사·변이·시각 회귀·서명 워크플로 진입 단계도 확인하므로 변이 단계가 없던 과거 실행이나 서명 진입점이 없는 실행은 통과하지 않는다. 현재 `master`의 서명 잠금 시점과 서명자 파일은 비어 있다. 이 상태에서 서명 워크플로 진입 단계는 비활성 안내를 출력하고도 성공할 수 있으므로, 단계 성공을 실제 커밋 서명 검증의 증거로 해석하지 않는다. 원격 생략 경로는 별도의 보호 경로 비교에 의존한다. GitHub 응답, 저장소, 이벤트, 워크플로 경로, SHA, 작업 이름·회차를 닫힌 목록으로 확인한다. 없거나 조회에 실패해도 거부한다. 토큰은 환경에서만 받고 공개 조회는 무인증도 사용한다.

작업 브랜치가 자기 워크플로와 그 정책 기대값을 함께 바꾸면 단계 이름과 성공만으로는 실제 명령을 증명하지 못한다. 원격 증거 경로는 API를 보기 전에 대상 트리와 신뢰한 로컬 `master` 트리를 비교한다. `master`의 에이전트 쓰기 허용 목록 밖의 파일, Cargo·패키지 명세와 잠금 파일, 빌드 진입점의 변경은 거부한다. 목록을 읽을 수 없거나 Git 객체가 없을 때도 거부한다. 두 증거 경로 모두 `docs/workflow.md` 2.8의 신뢰된 Git 사전 비교가 필요하다. 사전 비교에 포함된 검사기나 실행 경로가 바뀌면 로컬 영수증도 사용하지 않고 메인이 일반 전체 검사를 한다. 사전 비교 대상은 그대로이지만 그 밖의 보호 경로가 정당하게 바뀐 경우에는 검증된 로컬 서명 영수증을 쓸 수 있다. 이 비교와 게이트 자체가 작업 브랜치에 의해 바뀌지 않은 신뢰된 도구라는 전제는 별도로 필요하다. 제품 소스와 테스트 입력의 의미, 브랜치의 코드가 의도대로 동작하는지까지 경로 비교로 증명하지 않는다.

러너 미배정 상태의 종료, 취소, 시간 초과는 각각 재시도 대상으로 표시하되 실패를 반환한다. 실행 중은 대기, 검사 또는 준비 단계의 실패는 로그 확인 대상으로 구분한다. 성공으로 끝난 작업에 현재의 필수 단계가 없으면 빠진 작업과 단계 이름을 표시하고 실패한다. API가 시간 초과를 취소로만 나타내면 원인을 단정하지 않고 취소로 표시한다. `node harness/ci/remote-check.mjs <sha> --linux`는 Linux 작업과 세 필수 단계만 확인한다. 이 명령의 결과는 범위가 표시된 별도 값이며 병합 게이트가 받는 전체 성공 증거가 아니다.

병합 때는 `docs/workflow.md` 2.8의 조건을 전부 적용한다. `just merge-gate`는 실제 `master`와 병합 대상, 변경 경로, 검증된 증거, 리뷰 기록의 원격 도달 가능성을 확인하고 `check-fast-static`을 실행한다. 정상 커밋 훅도 실제 커밋 인덱스를 받아 이 판정을 반복한다. 게이트 요청이 없으면 일반 전체 검사를 유지한다. 조건이 맞지 않는 경우 생략을 거부한다.

로컬 영수증의 단순 JSON만으로 검사 실행 여부를 증명할 수 없다. 같은 SHA와 `exit: 0`을 적은 위조 파일과 정상 파일이 비트 단위로 같을 수 있기 때문이다. 따라서 `master`의 신뢰 서명자로 검증되는 분리 서명을 추가로 요구한다. 서명자가 없으면 로컬 영수증은 사용할 수 없다. 이는 서명자의 진술을 신뢰하는 경계이며 서명자가 거짓 진술을 하는 경우까지 증명하지 않는다. 현재 `harness/allowed_signers`는 비어 있어 기존 JSON 하나만으로는 생략할 수 없다. 원격 결과는 GitHub의 실행 보고와 기준 `master`의 검사 정의를 신뢰한다.

로컬 객체 저장소에는 있지만 푸시된 참조에서 도달할 수 없는 과거 리뷰 SHA는 원격에서 사라질 수 있다. 게이트는 리뷰·진행 기록의 SHA를 브랜치 끝의 조상이나 GitHub가 광고하는 태그의 조상으로 제한한다. 일시 브랜치에만 있는 객체는 브랜치가 삭제되면 새 체크아웃에 나타나지 않는 반례를 확인했다. 예전 T-03의 세 SHA는 2026-11-18 무인증 `ls-remote`에서 `review-evidence/t-03-r1`, `r2`, `r3` 태그로 확인했다. 태그도 삭제할 수 있으므로 메인이 기록 참조 기간에 보존하고, 태그가 사라지거나 원격 조회에 실패하면 닫힌다. 리뷰를 받은 커밋은 합치거나 다시 쓰지 않는다.

## 실측과 한계

2026-11-18 공개 GitHub API `ci.yml` 최근 완료 push 8건의 Linux 작업 대기는 4~5초, 실행은 225~234초였다. macOS 작업 대기는 1~304초, 실행은 900~1,417초였다. 이 16개 작업은 실패 또는 취소된 실행이므로 성공 완료 시간으로 해석하지 않는다. 같은 날 공개 API와 T-03 태그 조회는 인증 없이 성공했다. macOS의 `sandbox-exec`에서 네트워크 거부 프로필로 `/usr/bin/true`는 종료 0, 실측 벽시계 0.01초였다. 저장소의 네트워크 차단 프로필을 적용한 `nc`의 `1.1.1.1:443` 연결은 `Operation not permitted`로 종료 1, 벽시계 0.02초였다. 이것은 원격 러너의 샌드박스 기능이나 전체 네트워크 차단 테스트의 성공을 증명하지 않는다.

동시 5개 작업 브랜치의 대기와 전체 완료 시간은 실행하지 못했다. 다른 브랜치를 이 작업에서 푸시할 권한이 없으므로 추정치를 실측으로 적지 않는다. GitHub macOS 러너 가용량과 소요는 실제 푸시 뒤 확인해야 한다.

별도 작은 작업 공간에서 0.4초씩 실행하는 테스트 6개를 nextest로 실행했다. `just`가 `NEXTEST_TEST_THREADS`를 지우는 조건에서 이벤트 12개를 집계한 결과 최대 동시 실행은 4개였고 6개 모두 통과했다. 최초 측정의 여러 프로세스 로그가 섞여 집계에 실패해 한 번의 쓰기로 기록하도록 고쳐 재측정했다.

메인이 확인한 H-49의 [원격 실행 2차](https://github.com/gihwan-dev/stock-copilot/actions/runs/44096262667/attempts/2)는 Linux 14분 11초 성공, macOS 65분 50초 실패다. 메인 보고에 따르면 macOS의 전체 테스트 2,034개는 928.8초, 커버리지 1,115개는 261.8초로 모두 통과했고 승인된 테스트 준비 변경 두 건의 `test-diff`만 실패했다. API에서 확인한 각 작업 시작은 실행 시작 후 Linux 8초, macOS 10초다. 이전 8건의 실패·취소 시간보다 긴 실제 사례이므로 15~23분을 성공 예상 시간으로 쓰지 않는다.

[U-03 병합 `66ea753`의 원격 실행](https://github.com/gihwan-dev/stock-copilot/actions/runs/44129273477)은 macOS가 성공했으며 워크플로 시작부터 종료까지 49분 37초였다. API의 macOS 작업 시작은 워크플로 시작 5분 5초 뒤이고 작업 시작부터 종료까지는 44분 32초다. 이어진 [D-49 병합 `d235aaf` 1차](https://github.com/gihwan-dev/stock-copilot/actions/runs/44141922108/attempts/1)에서 Linux는 13분 57초에 성공했지만, macOS는 러너 ID가 0이고 실행 단계가 없는 채 15분 1초 뒤 취소됐다. 해당 작업의 GitHub 주석은 러너 미배정과 macOS ARM 용량 부족을 명시한다. 처음 조회했을 때 2차는 macOS가 대기 중이었고, Linux의 이전 성공 작업이 2차 응답에도 보존돼 있었다. 이후 [2차 실행](https://github.com/gihwan-dev/stock-copilot/actions/runs/44141922108/attempts/2)은 Linux·macOS 모두 성공했고 macOS 작업은 44분 22초였다. 다만 당시 워크플로에는 현재 필수인 `diff mutants` 단계가 없어 새 원격 전체 판정은 그 성공을 거부한다. 이 한 사례만으로 모든 재시도 형태의 API 동작을 일반화하지 않는다.

| 범위 | 이 근거로 확인할 수 있는 것 | 별도로 필요한 것 |
|---|---|---|
| Linux 부분 결과 | 같은 SHA의 Linux 정적 검사, 컨테이너 시각 회귀와 네트워크 차단 Linux 테스트. `d235aaf`에서 실제 13분 57초 성공 | macOS·서명 작업·변이·전체 커버리지의 성공은 포함하지 않는다 |
| 로컬 macOS `just check` | 같은 SHA에서 전체 nextest·정해진 커버리지와 macOS 전용 코드·sandbox 경로. H-52 구현 커밋에서 2,059개와 커버리지 1,115개가 통과했다 | 실제 Tauri 앱 빌드·WKWebView 실측, Linux 컨테이너 시각 회귀와 별도 `mutants-diff`는 이 영수증에 포함되지 않는다 |
| Linux와 로컬 macOS의 조합 | 같은 SHA의 Linux 부분 결과와 신뢰 가능한 로컬 전체 검사 영수증을 각각 확인할 수 있다 | 서명 워크플로와 같은 SHA·기준의 변이 결과도 별도로 필요하다. 자동으로 이 세 증거를 합산하는 병합 경로는 아직 없으며 기존 원격 전체 판정은 그대로다 |

Linux는 `src-tauri`, `e2e-app`, `platform-macos`, `secrets-keychain`, CommonCrypto를 요구하는 `store-sqlite`와 macOS sandbox 테스트 모듈을 제외한다. 변이 대상에는 `store-sqlite`도 있으므로 Linux에서 모든 변경분 변이를 대체할 근거가 없다. 메인의 로컬 전체 검사 또는 스레드의 SHA 일치 영수증을 macOS 증거로 쓰는 방안은 유효하지만, 로컬 영수증을 자동 판정에 쓰려면 신뢰 서명이 필요하며 현재 서명자 목록은 비어 있다. 따라서 실측하지 않은 Linux 변이 대체나 서명 없는 영수증을 전체 성공으로 취급하지 않는다.

GitHub의 [러너 한도](https://docs.github.com/en/actions/reference/limits)는 Free 표준 러너 전체 20개, macOS 5개 동시 작업이다. [공개 저장소 러너](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)는 무료이며 `macos-15`는 3코어 M1·메모리 7GB다. 다음은 실측이 아니라 H-49의 실패 시점 65분 50초가 각 작업에 똑같이 걸린다는 가정의 산술 시나리오다. 실제 5개 브랜치 동시 실행·대기와 성공 소요는 미측정이다.

| 사용 가능한 macOS 슬롯 | 5개 작업의 마지막 작업이 해당 실패 시점에 도달하기까지, 대기 외 가정 |
|---|---|
| 5개 | 약 65분 50초, 모두 즉시 시작할 때 |
| 2개 | 약 3시간 17분 30초, 세 묶음으로 실행할 때 |
| 1개 | 약 5시간 29분 10초, 순차 실행할 때 |

변경분 변이에는 별도의 최대 20분 실행 제한이 있다. 단순히 H-49의 65분 50초에 그 상한을 더하면 85분 50초이며, 남은 후속 검사·대기·실행 시간 변동은 포함되지 않는다. 기존 90분 작업 제한은 여유가 작아 120분으로 늘렸다. 이것은 속도 개선이나 실제 성공 보장이 아니다.

속도 대안으로 macOS 전체 테스트와 커버리지·변이를 별도 작업으로 나누면 한 브랜치의 작업을 겹칠 수 있지만, 다섯 슬롯을 공유하는 다섯 브랜치에서는 추가 대기와 도구 설치·컴파일 중복이 생긴다. Linux로 옮길 수 있는 TypeScript·정적 검사는 이미 중복되는 부분이 있지만, macOS 샌드박스와 플랫폼 전용 테스트를 Linux 결과로 대체할 근거는 없다. 현재 `cargo-mutants`는 고정 버전을 `cargo install --locked`로 설치하고 lefthook은 고정 SHA-256으로 확인한다. 도구 설치 결과를 캐시하려면 OS·아키텍처·버전과 출처 무결성, 브랜치 간 신뢰 경계 및 실제 적중률을 먼저 확인해야 한다. 3코어 macOS에서 고정 동시 테스트 4개가 시간을 늘리는지도 미측정이다. H-51에서 컴파일 공유를 다룬다. 새 캐시 도구나 검사의 생략은 이 초안에서 도입하지 않는다.

## 승인된 기존 테스트 준비 변경

`test-diff`의 예외는 `harness/test-diff/approvals.toml`의 행으로 표현한다. 실제 승인 파일은 메인이 `master`의 단일 부모 직접 커밋에서 작성한다. 승인 파일을 바꾸는 커밋은 승인 대상 테스트 파일을 함께 바꾸지 않는다. 검사는 작업 브랜치의 파일이 아니라 원격 `master`의 기존 첫 부모 이력에서 기록을 읽는다. 기록이 병합으로 도입·변경됐거나 검사 대상 커밋이 자기 승인 기록을 함께 도입했으면 거부한다. 현재 승인 목록에 있는 테스트 파일이 과거의 승인 파일 변경 커밋에서 함께 바뀌었어도 보수적으로 거부한다. 얕은 저장소와 확인할 수 없는 이력도 거부한다. 과거 master 커밋은 이후 메인이 기록한 승인을 적용할 수 있으나 해당 커밋이 현재 원격 master의 첫 부모 이력에 있어야 한다. 이는 원격 master를 메인이 관리한다는 신뢰 경계이며 브랜치에 같은 TOML을 적는 행위는 권한을 만들지 않는다.

로컬 판정은 `origin/master`가 신뢰할 수 있는 fetch 결과라는 전제에 의존한다. 로컬 원격 추적 참조를 작업자가 직접 위조하면 로컬 훅은 속일 수 있다는 반례가 재현됐다. GitHub CI는 실제 원격 참조로 새 체크아웃하고 병합 게이트는 원격 성공을 독립적으로 확인한다. 최신 승인 커밋을 HEAD로 둔 `master`의 병합 준비에서는 해당 승인을 사용할 수 있지만, 그 승인 커밋이 승인된 테스트 파일을 함께 바꿨다면 여전히 거부한다.

승인 커밋과 테스트 커밋을 작업 브랜치에서 만들고 원격 `master`에 fast-forward해 버리면 첫 부모 이력만으로 직접 승인과 구별하지 못하는 반례도 실행했다. 이 설계는 메인이 원격 `master`를 관리하고 작업을 `--no-ff`로 병합한다는 경계에 의존한다. fast-forward 전의 로컬 및 푸시 검사는 이전 원격 추적 참조로 자기 승인을 거부한다. 이미 원격 권한이 넘어간 뒤의 무단 갱신은 별도 원격 권한·서명 정책이 필요하다.

각 행은 `task`, `path`, `before_sha256`, `after_sha256`, `finding`, `decision`, `reason`을 가진다. 정확한 전·후 파일 바이트와 해당 파일의 실제 지적 집합이 승인 목록과 일치해야 한다. `modified`와 함수의 `support-modified`만 대상이다. 기존 테스트의 단언 문장과 순서, 속성·시그니처를 보존하고 조기 반환·조건·반복 등 제어 흐름으로 우회하는 준비 코드는 거부한다. 단언 매크로와 `assert*`, `check`, `check_*`, `verify*` 이름의 보조 호출을 포함한 문장을 보존한다. 그 밖의 이름으로 감춘 의미상의 단언이나 준비 함수의 의미가 약해졌는지는 메인이 정확한 파일 차이를 검토한다. 단언 삭제, 테스트 삭제, 목록 누락, 개수 감소, 미도달 등은 승인 행이 있어도 통과하지 않는다. 기존 `test-changes` 서명 검사는 바꾸지 않는다.

이 승인 판정기로 H-49의 두 과거 Git 트리를 평가하는 회귀는 통과한다. 다만 GitHub에서 `0e10f05`의 기존 실행을 그대로 재실행하면 그 커밋에 있던 이전 판정기를 다시 실행한다. 따라서 현재 승인 파일만 추가해도 과거 실행은 고쳐지지 않는다. 새 판정기가 포함된 후속 커밋의 CI와 별도의 현재 판정기 기반 과거 트리 평가는 서로 다른 증거다. 후자의 원격 워크플로는 구현하거나 성공으로 주장하지 않는다.

## 버린 대안과 위험

- SHA가 적힌 JSON만 신뢰: 위조를 판별할 수 없어 버렸다.
- 이전 성공 한 건만 조회: 이후 실패·취소가 있어도 통과할 수 있어 최신 실행과 그 회차의 모든 필수 작업을 확인한다.
- 로컬 Git 객체 존재만 확인: 원격 체크아웃에 없는 옆가지 객체를 통과시킬 수 있어 원격 참조를 직접 확인한다.
- Linux만으로 전체 판정: macOS 전용 crate와 sandbox 경로를 실행하지 못한다.
- 변경된 문서도 모든 소비 테스트를 다시 실행: 중복 생략 결정과 충돌한다. 대신 해당 문서 차이는 정적 검사만 다시 하므로 문서가 런타임 테스트의 입력인 경우에도 전체 재실행을 하지 않는 잔여 위험이 있다.
- 푸시 훅을 바로 빠른 검사로 낮춤: 병합 생략 이외의 검사 완화 승인에 해당하지 않아 보류했다.

- H-51: 컴파일 공유 및 병행 `justfile` 변경과의 통합을 메인이 확인한다. H-52는 외부 스레드 환경 변수가 제거되는 경로에도 4개 제한이 적용되도록 `.config/nextest.toml`과 그 고정 검사·예제를 바꾼다.
