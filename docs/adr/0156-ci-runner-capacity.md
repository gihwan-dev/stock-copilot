# ADR 0156: H-59 원격 변이 검사의 러너 점유 상한

- 상태: 확정 (2026-11-23)


## 배경

2026-11-22의 주간 전체 변이와 일간 실행이 겹쳐 병합 판정용 CI가 macOS 실행 자리를 기다렸다. 한 matrix의 `max-parallel`만 제한하면 별도 주간·일간 실행은 동시에 각각 두 자리를 차지할 수 있다.

## 결정

주간·일간 변이 matrix 각각에 `max-parallel: 2`를 둔다. 계정의 다섯 자리 중 변이가 최대 두 자리를 사용해 나머지 세 자리를 다른 작업에 남기기 위한 값이다. 두 종류가 동시에 두 자리씩 쓰지 않도록 합산 점유를 두 자리로 묶되, 1차 리뷰·비판에서 확인된 대로 워크플로 최상위 `concurrency`를 쓰면 48시간 이상 도는 주간 변이 뒤에 일간 실행 전체가 대기하게 되어, `changes` 작업의 `ci-range.mjs changed`가 실행 시점의 `Date.now()` 기준으로 지난 24시간을 계산하면서 매일 도는 `macos` 전체 검사(`just base=HEAD check`)가 건너뛰어지고 `linux`도 지연된다.

따라서 `nightly.yml`의 최상위 `concurrency`는 제거하고, 변이 작업인 `jobs.mutants`와 `jobs["mutants-daily"]`에만 작업 단위 2슬롯 `concurrency`를 둔다. 각 조각 번호(`matrix.shard`, 예: `0/128`..`127/128` 또는 `0/8`..`7/8`, 단일 조각 `0/1`)의 일의 자리 홀짝으로 두 개의 고정 슬롯 그룹(`${{ github.workflow }}-mutants-slot-0`, `slot-1`, `queue: "max"`, `cancel-in-progress: false`)에 매핑한다. 이렇게 하면 주간과 일간 변이가 겹쳐 실행되더라도 두 그룹 각각에 동시에 최대 1개씩만 실행되므로 변이 작업의 macOS 합산 점유는 항상 2개 이하로 제한되며, 일간 실행의 `changes`·`macos`·`linux`·`notify` 작업은 변이 대기열의 영향을 받지 않고 예정 시각에 즉시 실행된다. 주간 128조각은 두 슬롯에 정확히 64/64로 균등 분배되고 일간 1~8조각도 2슬롯을 넘지 않는다. 일간 실행의 일반 macOS 검사는 변이 두 자리와 별개이므로 같은 일간 실행에서 macOS 작업 최대 세 개가 돌 수 있다. 계정 전체의 다른 작업까지 예약하거나 CI에 우선순위를 주는 기능은 아니어서 CI 대기가 절대로 없다고 보장하지 않는다.

CI는 브랜치별 그룹을 쓰고 master가 아니면 같은 그룹의 이전 실행을 취소한다. master는 `cancel-in-progress: false`만으로는 대기 중 실행이 교체될 수 있으므로 실행 ID와 재시도 번호로 그룹을 고유화한다. GitHub concurrency 그룹과 [표현식의 문자열 비교](https://docs.github.com/en/actions/reference/workflows-and-actions/expressions)는 대소문자를 구분하지 않는다. 따라서 `Master`처럼 master와 대소문자만 다른 비-master 브랜치는 master처럼 취급돼 이전 실행이 취소되지 않고, `feature/Foo`와 `feature/foo` 같은 두 비-master 브랜치는 서로의 실행을 취소할 수 있다. 현재 워크플로 최상위 concurrency에서는 사전 작업의 출력을 참조할 수 없으므로 이름을 대소문자 보존 해시로 변환하지 않았다. 메인은 해당 이름 충돌을 피하거나 별도 실행 조정 방식을 결정해야 한다.

GitHub의 [concurrency 문서](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)에 따르면 `queue: max`는 대기 실행 100개까지 보존하며 가득 차면 추가 실행이 취소된다. 대기 순서는 그룹 진입 시각 기준이고 원래 예약 순서를 보장하지 않는다. GitHub의 [실행 한도](https://docs.github.com/en/actions/reference/limits)는 대기 시간을 포함한 워크플로 실행을 최대 35일로 제한한다. 별도 저장소에서 도는 워크플로와 이 설정이 반영되기 전에 시작한 실행은 이 대기열로 제한되지 않는다. 이 설정은 검사 내용과 각 작업의 제한 시간을 변경하지 않는다.

## 소요 시간과 제안

[2026-11-22 주간 실행](https://github.com/gihwan-dev/stock-copilot/actions/runs/45067223646)은 128개 중 18개 성공, 2개 실패, 108개 취소였다. 실제 작업 단계가 실행되고 성공한 18개의 시작부터 종료까지 중앙값은 45.3분, 평균은 46.4분(최소 15.9분, 최대 86.4분)이었다. 취소된 미배정 조각의 시작·종료 시각은 실행 시간으로 세지 않았다. 이 표본을 128개에 단순 적용하면 두 자리에서 64파에 중앙값 약 48.3시간, 평균 약 49.5시간이 걸린다. 먼저 끝난 조각만 관찰한 표본이어서 편향이 있고 나머지 조각의 시간과 실제 완료는 미확인이다. 추가로, 고정 홀짝 슬롯은 두 슬롯 합 중 큰 쪽(`max(sum(slot-0), sum(slot-1))`)에 의해 완주 시간이 결정되며, GitHub Actions가 concurrency 대기 중인 matrix 작업을 `strategy.max-parallel: 2` 자리에 포함한다면 한 슬롯이 먼저 끝났을 때 다음 조각이 다른 슬롯 대기열에 막혀 빈 슬롯이 생길 수 있다(파당 소요가 `E[max(X, Y)]`에 가까워져 추정이 늘어날 수 있음). 이 상호작용 여부는 실제 주간 실행의 작업 타임스탬프로 확인한다.

180분 제한은 전체 워크플로가 아니라 각 주간 작업에 적용된다. 모든 조각이 제한 가까이 점유한다면 64파에 최대 약 192시간이 걸려 7일 주기를 넘으며, 제한 도달 조각은 성공하지 못한다. 대기열 직렬화는 전체 변이 동안 일간 실행의 신선도를 늦춘다. 실제 완주 시간과 일간 대기열을 관찰한 뒤 주간 전체 실행을 격주로 옮기거나 조각별 부하 균형을 조정하는 방안을 제안한다. 조각 수·실행 주기·검사 범위는 이번에 임의 변경하지 않는다.

일간 계획은 변이 수에 따라 1~8개 조각이므로 두 자리에서는 조각 수를 2로 나누어 올림한 횟수, 최대 4파가 필요하다. 이전 일간 실행의 단일 조각은 [11월 21일 UTC](https://github.com/gihwan-dev/stock-copilot/actions/runs/44957369568/job/137008758100) 2분 44초, [11월 20일 UTC](https://github.com/gihwan-dev/stock-copilot/actions/runs/44837013950/job/136636526235) 2분 59초였다. 변이 수와 분포를 확인하지 못했으므로 일반적인 일간 완료 시간을 추정할 근거가 되지 않는다. 일간의 조각별 작업 제한 360분을 모두 채우는 경우 최대 24시간에 계획·대기 시간이 더해지고, 제한에 걸린 조각은 성공하지 못한다. 이러한 상태가 반복되면 일간 주기도 따라잡지 못하므로 조각별 부하를 재조정하거나 검사 주기를 바꾸는 방안을 제안한다. 변이 수를 확인할 수 있는 일간 실행을 관측해 예상치를 다시 잡는다.

## 검증과 인계

matrix 상한의 1·2 허용과 0·분수·3·누락 거부, `nightly.yml` 최상위 concurrency 금지 및 `changes`/`macos`/`linux` 비차단, `mutants`·`mutants-daily` 작업 단위 2슬롯 공통 대기열과 홀짝 분배, master 그룹의 고유성과 비-master 취소 조건을 정책 테스트로 고정한다. 두 워크플로의 새 concurrency와 두 matrix 상한을 제외한 JSON을 기존 파일과 비교해 단계·조건·시간제한이 동일함을 확인했다. GitHub에 푸시한 실행 및 실제 대기 시간은 메인이 확인한다.

정상 커밋 훅의 첫 시도에서 기존의 전체 strategy 객체 비교 두 건이 새 필드를 예상하지 못해 실패했다. 사전 승인된 고정 기대값 갱신으로 `harness/ci/tests/h42-nightly.test.mjs`의 주간 strategy 기대 객체와 `harness/ci/tests/h47-schedule.test.mjs`의 일간 strategy 기대 객체에 각각 `max-parallel: 2`를 추가한다. 기존 단언과 다른 기대 필드는 그대로 유지한다.
