# 작업 절차 (v0.2)

모든 구현 작업은 이 절차를 따른다. 예외는 없다. 절차를 강제하는 훅과 설정은 [harness.md](harness.md) 7장에 있다.

## 1. 역할

| 역할 | 누가 | 하는 일 | 강제 |
|---|---|---|---|
| 메인 에이전트 | 사용자와 대화하는 세션 | 작업 선정, 브리프 작성, 평가, 수정 여부 판단, 리뷰 기록, 푸시, 사용자 보고. 코드를 직접 쓰지 않는다 | 편집 훅이 메인에게 `docs/**`(보호 문서 제외)만 허용 |
| 구현 에이전트 | T3의 새 Codex `gpt-6.1-sol` 또는 `gpt-6.1-terra`(메인이 스레드를 띄울 때 정한다). sol high, terra max (별도 작업 사본) | 작업 하나를 구현하고 `just check`를 통과시킨다 | Codex 종료 훅이 적용된 세션에서는 `just check`를 돌린다 |
| 적대적 리뷰어 | T3의 새 Opus 5.5 (`adversarial-reviewer`, 별도 작업 사본) | 구현을 깨뜨릴 방법을 찾고 등급을 매긴다. 판정하지 않는다 | 읽기 전용 지시, T3 격리 사본, 메인의 대상 스냅숏 재확인 |
| 비판자 | T3의 새 Codex `gpt-6.1-sol` (별도 작업 사본) | 리뷰 지적을 하나씩 실행으로 반박해 본다 | 리뷰어와 같음 |

"새"는 앞 단계의 대화 맥락을 물려받지 않는다는 뜻이다. 각 에이전트는 브리프와 저장소만 본다. native Claude Agent 위임은 허용하지 않는다. T3 Codex는 `target.driverKind=codex`다. 구현·수정 회차는 T3 Codex `gpt-6.1-sol` 또는 `gpt-6.1-terra`(메인이 스레드를 띄울 때 정한다)가 한다. 기본 추론 강도는 sol은 high, terra는 max다. 조사·비판은 `gpt-6.1-sol`(high), 적대적 리뷰는 Claude Opus 5.5다. 구현 위임은 `role=implementation`을 명시한다. Terra는 이 역할에서만 허용하며 역할 생략·research·review(비판)는 sol만 받는다. 적대적 리뷰는 `target.driverKind=claudeAgent`, `target.model=claude-opus-5-5`, `role=review`다. 모두 `isolation=worktree`다. 포크와 재개는 쓰지 않는다.

## 2. 순서

```
1. 브리프      메인이 작업 단위 하나를 골라 브리프를 쓴다
2. 구현        implementer가 구현하고 just check를 통과시킨다 (또는 "막힘")
3. 적대적 리뷰  adversarial-reviewer가 지적 목록을 만든다
4. 비판        review-critic이 지적마다 확정·기각·불확실을 판정한다
5. 평가        메인이 지적별로 수정·보류·기각을 결정한다
6. 수정        같은 Codex 스레드에서 수정할 수 있다. 차단·중요 등급을 고쳤으면 3으로 돌아간다
7. 완료        메인이 리뷰 기록과 tasks.md를 갱신하고 푸시한 뒤 사용자에게 보고한다
```

- 병합은 메인 에이전트가 `git merge --no-ff`로 한다. 병합 커밋도 훅의 검사를 거친다. 2.8의 조건을 통과한 경우 정적 검사만 다시 한다. fast-forward가 된 경우에는 병합 직후 `just base=<병합 전 기준 브랜치 끝> check`를 돌린다 (ADR 0015).
- 검사 명령은 `just base=<HEAD 또는 40자리 커밋 ID> check`다. 브리프의 기준 커밋을 `base`로 준다 (ADR 0013).
- 푸시는 메인 에이전트만 한다. 서브에이전트는 푸시하지 않는다. CI의 서명 검사는 푸시 뒤에 도는 사후 탐지다 ([harness.md](harness.md) 7.6).

### 2.1 브리프

메인 에이전트는 새 작업의 브리프를 쓰기 전에 `main`의 CI가 통과 상태인지 확인한다. 실패면 멈추고 사용자에게 보고한다. CI가 아직 없으면(H-16 이전) 이 확인은 건너뛴다.

메인 에이전트가 쓴다. 양식:

```markdown
# 브리프 <작업 ID> <제목>
- 기준 커밋: <SHA>
- 브랜치: <대상 작업 브랜치>
- 완료 기준 (tasks.md 그대로. 각 기준은 통과·실패로 판정할 수 있어야 한다)
  1. ...
- 관련 요구사항: SEC-.., ORD-..   관련 구조 규칙: architecture.md x.y
- 손댈 범위: crates/<name>/src/**, crates/<name>/tests/**
- 손대면 안 되는 범위: (보호 경로 외에 추가로)
- 정해진 결정: ADR-NNNN
- 검사 명령: just check
- 막혔을 때: 보고서 첫 줄을 "막힘:"으로 시작하고 멈춘다
```

| 항목 | 이유 |
|---|---|
| 기준 커밋 SHA | 리뷰어와 비판자가 같은 기준으로 `git diff`를 만든다. 테스트 변경 검사(`xtask test-diff`)의 기준이기도 하다 |
| 통과·실패로 판정할 수 있는 완료 기준 | 검사로 돌아오는 기준이 있어야 증거를 낼 수 있다 |
| 검사 명령 | 증거로 낼 명령을 정해 둔다 |
| "막힘:" 출구 | 억지로 통과시키는 대신 멈출 수 있는 정상 출구다. 사람에게 넘기는 출구를 주면 편법이 줄었다는 연구가 있다 (R-10 Q6) |

- 브리프에 구현 방법을 지시하지 않는다. 무엇이 참이어야 하는지만 쓴다.
- 작업 크기: 완료 기준 3~5개, crate나 기능 폴더 하나에 들어가는 크기. 이것은 리서치의 1차 근거가 아니라 판단이다 (R-10 Q8).
- 메인은 이어지는 작은 작업을 한 브리프로 묶을 수 있다. 각 작업 ID의 리뷰 기록·ADR·progress 행은 따로 남긴다.
- 메인은 브리프에 `리뷰 등급: N`을 적는다. 생략하면 3이다. 등급 3은 하네스, 보안·권한, 금액·수량·환율 계산, 주문 관련이며 최대 3회차다. 등급 2는 일반 유스케이스·저장소·외부 연동이며 최대 2회차다. 등급 1은 문서·기계적 연결·화면 배치·표시이며 1회차다. 구현자가 계산·보안 범위를 발견하면 등급을 올릴 수 있으나 내릴 수 없다.

### 2.2 구현

- 작업 하나에 브랜치 하나, 커밋은 작게. 구현 에이전트는 푸시하지 않고 서명 옵션을 쓰지 않는다.
- `just check`가 통과해야 끝난 것이다. 통과시키기 위해 검사를 끄거나 테스트를 지우거나 약하게 만들지 않는다. 기존 테스트의 삭제·변경은 `xtask test-diff`가 실패시킨다.
- 하네스가 막으면 우회하지 않고 멈춘 뒤 "막힘:"으로 보고한다 ([harness.md](harness.md) 8장).
- Codex Stop 훅이 적용된 세션은 전체 검사를 돌린다. 실패하면 계속 고치게 하고, 계속된 회차가 "막힘:"으로 보고하면 실패 상태로 끝낼 수 있다. T3가 훅을 적용하지 않은 세션에서는 메인이 직접 검사와 대상 스냅숏을 확인한다.
- 보고 형식: 첫 줄 "완료" 또는 "막힘: <한 줄 이유>", 커밋 SHA와 바꾼 파일, 완료 기준별 충족 근거(테스트 이름, 명령과 출력), `just check` 마지막 요약 줄, 확신이 없는 부분과 범위 밖에서 발견한 문제.

구현이 끝나면 메인이 확인한다:

| 확인 | 기준 |
|---|---|
| 하네스 기록 | 실제 종료 코드와 `just check` 출력이 있는가. T3 Codex 결과를 Claude의 `PostToolUse(Agent)` 기록으로 취급하지 않는다 |
| 실제 모델 | 구현·수정은 메인이 정한 sol 또는 terra, 조사·비판은 sol, 적대적 리뷰는 Opus 5.5인가. 실제 사용한 구현 모델과 추론 강도를 기록했는가 |
| 범위 | 대상 커밋의 변경 파일이 브리프의 "손댈 범위" 안에 있는가 |
| 작업 사본 | `git status`에 커밋되지 않은 파일, 특히 보호 대상이 될 새 파일이 없는가 |
| 막힘 | "막힘:"이면 2.7로 간다 |

### 2.3 적대적 리뷰

리뷰어에게 주는 것:

| 준다 | 주지 않는다 |
|---|---|
| 작업 브랜치가 있는 브리프, 기준 커밋 SHA, 대상 커밋 SHA | 구현 에이전트의 보고서 |
| 저장소 | 메인이 요약한 변경 차이 |

- 리뷰어 사본은 T3의 작업 사본 격리로만 만들고 메인 저장소 안에는 만들지 않는다. 리뷰어는 하위 에이전트를 띄우지 않는다. 리뷰어는 격리된 작업 사본에서 `git checkout --detach <대상 SHA>`를 한 뒤 `git diff <기준 SHA>...HEAD`로 변경을 직접 본다. 메인의 요약도 편향이 되므로 주지 않는다.
- 구현자의 설명을 주지 않는 이유: PR 설명을 다듬어 보안 판정을 바꾸는 공격이 Claude Code 리뷰 파이프라인에서 33건 중 32건 성공했다는 연구가 있다 (R-10 Q4).
- 재현용 파일은 작업 사본 안에만 만든다. 원본은 리뷰 대상 작업 사본이다. 시작 시 브리프의 작업 브랜치에 해당하는 등록된 작업 사본을 고정해 추적 파일·인덱스·HEAD·HEAD 참조를 비교하며, 다른 등록 작업 사본과 리뷰어 자신의 초기 체크아웃은 비교하지 않는다. native 호환 훅의 종료 비교는 대상 변경을 차단한다. T3 리뷰의 자동 훅 적용으로 간주하지 않는다. 메인은 T3 위임 전후 대상의 파일 내용·인덱스·HEAD·참조 스냅숏을 직접 비교한다. 대상을 확인하지 못하면 원인을 보존한 `unchecked`이며 오염으로 단정하지 않는다. 이 경우 메인은 브리프와 대상 등록을 확인하고 리뷰를 다시 시작한다.

리뷰어의 목표는 승인이 아니라 결함을 찾는 것이다. **리뷰어는 판정하지 않고 등급만 매긴다.** "큰 문제가 아니다"라고 스스로 설득해 승인하는 실패를 구조로 막기 위해서다. 확인할 것:

- 완료 기준을 실제로 충족하는가. 테스트가 기준을 정말 검증하는가
- 잘못된 입력, 경계값, 순서 바뀜, 동시 실행, 부분 실패, 재시도에서 깨지는가
- 주문·금액·비밀 값과 닿는 변경이면 design.md의 SEC, ORD, ACC 항목을 어기는가
- 구조 규칙을 문자 그대로는 지키면서 취지를 어기는가
- 기존 테스트의 삭제·약화, 건너뛰기
- 새로 생긴 검사 끄기마다 규칙을 지키는 다른 방법이 없었는가 ([harness.md](harness.md) 2.1). 끄기 목록을 리뷰 기록에 적는다
- [harness.md](harness.md) 9장 "리뷰에서 확인할 항목" 중 이 변경에 해당하는 것 전부

등급:

| 등급 | 기준 |
|---|---|
| 차단 | 완료 기준 미충족, SEC/ORD/ACC 위반, 데이터 손상 가능, 검사 우회나 테스트 약화 |
| 중요 | 특정 입력·순서·동시성에서 틀린 결과나 오류 누락 |
| 사소 | 동작은 맞지만 다음 변경에서 결함을 부르기 쉬운 것 |

지적 형식: 번호, 등급, 파일과 줄, 재현 명령과 실제 출력(또는 반례 입력과 기대값·실제값), 근거(위반한 기준이나 문서 위치), "추정" 여부. 재현하지 못한 지적은 "추정"으로 표시하고 재현에 필요한 것을 쓴다. 형식, 이름, 취향, 린터가 잡는 것, 변경 전부터 있던 문제는 지적하지 않는다.

리뷰가 끝나면 메인은 원본 작업 사본의 `git status`와 HEAD가 리뷰 전과 같은지 확인한다. 다르면 다음 단계로 가지 않고 사용자에게 보고한다.

### 2.4 비판

비판자에게 주는 것: 대상 작업 브랜치가 명시된 브리프, 기준·대상 커밋 SHA, 리뷰 지적 목록, 저장소. 구현자의 보고서는 주지 않는다.

비판자는 토론하지 않고 실행으로 검증한다. 지적마다 먼저 반박을 시도하고, 반박이 안 되면 직접 재현한다.

- **확정**: 재현했거나 코드로 확인했다. 명령과 출력, 또는 파일과 줄을 붙인다
- **기각**: 지적이 틀렸다. 반례 실행 결과나 파일과 줄을 붙인다. 근거 없는 기각은 하지 않는다
- **불확실**: 판정하려면 무엇이 더 필요한지 쓴다

등급이 결과와 맞지 않으면 고친 등급과 이유를 쓴다. 비판자는 리뷰어가 놓친 것을 발견하면 같은 형식의 추가 지적으로 덧붙인다.

### 2.5 평가

메인 에이전트가 한다. 지적별로 결정한다.

| 결정 | 조건 |
|---|---|
| 수정 | 확정된 차단·중요 등급. 확정된 사소 등급 중 고치는 비용이 작은 것 |
| 보류 | 확정됐지만 이 작업 범위 밖인 중요·사소 등급. tasks.md에 새 작업으로 추가한다. 차단 등급은 보류할 수 없다 |
| 기각 | 비판자가 근거를 붙여 기각했고 메인도 그 근거를 확인했다 |
| 추가 확인 | 불확실. 차단 등급이면 사용자에게 보고한다. 그 외는 메인이 명령을 돌려 직접 확인한다 |

- 리뷰어와 비판자의 등급이 다르면 재검토 여부는 높은 쪽 등급으로 정한다.
- 메인은 완료 기준 충족 여부를 지적과 별개로 다시 판단한다. 지적이 0건이어도 기준 미충족이면 반려한다.
- 메인이 비판자의 기각을 뒤집으면 이유를 기록한다 (3장 측정 항목).

### 2.6 수정과 재검토

- 수정은 같은 T3 Codex 스레드에 새 브리프를 보내 이어 갈 수 있다. 적대적 리뷰어는 매번 새 Claude 서브에이전트다.
- 수정 브리프에는 원래 브리프, 새 기준 커밋(앞 단계의 대상 SHA), 평가 결과, 고칠 지적을 넣는다.
- 차단이나 중요 등급을 고쳤으면 3단계부터 다시 한다. 리뷰어와 비판자도 새로 띄운다.
- 사소 등급만 고쳤으면 메인이 차이와 하네스 기록을 확인하고 끝낸다.
- 독립 리뷰·비판은 브리프의 등급을 상한으로 한다. 마지막 회차에서 실행으로 재현된 차단·중요 지적은 수정하고 추가 독립 리뷰 없이 수정 범위(기준 SHA → 수정 SHA), 회귀 검사와 변이 결과를 기록한다. 메인이 수정분을 평가한다.

### 2.7 "막힘" 처리

구현 에이전트가 "막힘:"으로 끝나면 메인은 이유를 보고 하나를 고른다.

| 이유 | 처리 |
|---|---|
| 작업이 너무 크거나 완료 기준이 서로 모순됨 | 작업을 쪼개거나 기준을 고쳐 새 브리프로 다시 시작한다. 완료 기준을 고치면 사용자에게 알린다 |
| 하네스 규칙이 정상 구현을 막음 | [harness.md](harness.md) 8장. 사용자에게 보고하고, 사람이 규칙을 바꾸기로 하면 ADR과 서명 커밋으로 바꾼다 |
| 기존 테스트가 틀렸다고 판단함 | 사용자에게 보고한다. 기존 테스트 변경은 사용자 서명 커밋으로만 들어간다 |
| `just check`를 3번 연속 통과하지 못함 | 실패 출력을 보고 새 브리프를 쓰거나 사용자에게 보고한다 |
| 하네스 기록이 `unchecked` (종료 훅이 검사하지 못함) | 메인이 `just check`를 직접 돌려 상태를 확인한 뒤 판단한다 |

### 2.8 병합 검사 생략

작업 브랜치 끝이 현재 `master`를 포함하고, 그 끝의 전체 검사 성공 증거가 동일한 40자리 SHA에 묶여 있으며, 준비된 병합 인덱스가 그 끝과 `docs/**`, `.codex/config.toml`, `harness/claude-hooks/hashes.json`, `harness/sandbox/**`, `harness/arch-check/cases.toml`만 다를 때만 병합 커밋의 전체 검사 재실행을 생략한다. 그때도 `check-fast-static`을 실행한다. 소스 차이, 충돌, 미스테이징 파일, 오래된 master나 다른 SHA는 거부한다.

메인은 병합을 준비하기 전에 신뢰된 Git으로 아래 명령을 실행한다. 검사기와 그 실행 경로가 `master`와 다르거나 확인에 실패하면 원격 결과와 로컬 영수증 모두를 이용한 생략을 거부하고 일반 전체 검사를 실행한다. `branch`에는 실제 브랜치 이름을 준다.

```sh
git --no-replace-objects diff --quiet --no-ext-diff --no-textconv master <branch> -- justfile lefthook.yml .github .claude .codex .cargo .config harness crates/xtask Cargo.toml Cargo.lock pnpm-lock.yaml .node-version rust-toolchain.toml
```

통과하면 메인은 `git merge --no-ff --no-commit <branch>`로 병합을 준비하고 문서·생성 등록을 스테이징한 뒤 `just merge-gate <branch>`를 실행한다. 이 명령은 같은 SHA의 GitHub `ci.yml`의 Linux·macOS 작업과 `signatures.yml`의 서명 작업이 해당 push 실행의 최신 회차에서 모두 성공했는지 직접 확인한다. Linux 검사·네트워크 차단 테스트·시각 회귀, macOS 전체 검사·변이, 서명 워크플로 진입 단계도 각각 성공해야 한다. 단계 성공만으로 서명 검사가 활성 상태였다는 뜻은 아니다. 실패·취소·진행 중·누락은 거부한다. `just remote-check <sha>`는 같은 원격 판정만 별도로 실행한다. 공개 조회는 인증 없이 가능하며 토큰이 필요한 경우 `GH_TOKEN` 또는 `GITHUB_TOKEN`을 환경에서만 받는다.

원격 성공을 증거로 사용할 때는 대상과 현재 로컬 `master`의 보호 경로도 비교한다. 기준 `master`의 `harness/agent-writable.txt` 밖의 파일이나 Cargo·패키지 명세, 잠금 파일, 빌드 진입점이 다르면 원격 성공과 관계없이 생략을 거부한다. 워크플로와 그 호출 도구를 작업 브랜치에서 바꾸고 같은 이름의 성공 단계를 만드는 경우를 막기 위한 조건이다. 정당한 하네스 변경도 이 경로에서는 일반 전체 검사를 받는다. 비교에는 대상 Git 객체와 메인이 관리하는 로컬 `master`가 필요하다. 메인은 명령과 비교 코드 자체를 `master`의 신뢰된 내용으로 실행해야 한다. 이미 병합 인덱스에 적힌 미검증 도구가 검사기 자체를 바꾸는 경우에는 그 도구의 자기 검사만으로 신뢰를 만들 수 없다.

러너를 배정받지 못했거나 작업이 취소·시간 초과로 끝나면 `remote-check`는 각각 재시도 대상으로 표시하고 실패한다. 실행 중에는 대기로 표시하고, 검사나 준비 단계 실패는 원인을 확인하도록 별도로 표시한다. 성공으로 끝난 실행에서 현재의 필수 단계가 빠졌다면 누락된 작업과 단계 이름을 표시하고 거부한다. `node harness/ci/remote-check.mjs <sha> --linux`는 같은 SHA의 Linux 작업과 필수 단계만 확인하며, 성공하더라도 macOS·변이·서명 검사나 병합 통과를 뜻하지 않는다. 병합 게이트는 이 부분 판정을 전체 원격 증거로 받지 않는다.

macOS 변경분 변이는 먼저 같은 기준의 목록을 만들고 한 조각에 최대 일곱 개가 되도록 네 개부터 128개까지 나누어 순서대로 실행한다. 각 조각의 계획과 실제 목록, 완주 결과를 확인하고 모든 조각이 성공해야 통과한다. 한 조각이 20분 제한을 넘으면 가능할 때 더 나누어 전체 조각을 다시 실행한다. 더 나눌 수 없거나 재시도도 제한을 넘으면 `RETRY_MUTATION_TIMED_OUT`으로 실패한다. 제한 전에 확인된 허용되지 않은 생존·시간 초과 변이는 코드 실패로 남긴다. 이전 워크플로의 일반 실패만으로 내부 제한 초과라고 추정하지 않는다. 같은 작업에서 순차 실행하므로 총 소요 시간은 원격 러너에서 따로 확인한다.

로컬 증거를 쓸 때도 위의 신뢰된 Git 사전 비교를 통과한 다음 `just merge-gate <branch> target/<작업 ID>/final-check.json`을 실행한다. `head`, `recipe: check`, `exit: 0`이 정확히 맞는 영수증과 옆의 `.sig`가 필요하다. 서명은 `stock-copilot-check` 네임스페이스에서 `master`의 `harness/allowed_signers`와 소유자 이름으로 검증한다. 서명 없는 JSON은 누구나 만들 수 있어 단독 증거로 받지 않는다. 신뢰 서명자가 비어 있으면 로컬 증거는 거부되고 원격 증거가 필요하다.

두 경로 모두 리뷰 기록과 진행 표가 가리키는 커밋이 작업 브랜치 끝의 조상이거나 GitHub가 실제로 광고하는 태그에서 도달 가능한지 확인한다. 일시 브랜치만으로는 병합 이후 새 체크아웃에서 객체가 유지되지 않는다. 태그 또한 지울 수 있으므로 기록이 참조하는 동안 메인이 보존하고 후속 병합 때 다시 확인한다. 로컬 Git 객체만으로는 원격 CI가 그 커밋을 가져올 수 없다. 원격 조회 실패도 거부한다.

게이트가 성공하면 메인이 정상 `git commit`을 실행한다. 게이트의 요청은 해당 작업 사본의 Git 관리 영역에 남고 커밋 훅이 SHA·인덱스·원격 참조·증거·정적 검사를 다시 확인한 뒤 소비한다. 병합을 중단하면 다음 커밋 가드가 남은 요청을 지우고 일반 전체 검사를 실행한다. 요청이 없는 일반 병합도 기존 전체 검사를 실행한다. 증거가 실패했거나 요청 뒤 상태가 바뀌었다면 커밋을 거부한다.

### 2.9 승인된 테스트 준비 변경

기존 테스트 준비를 바꾸기로 메인이 승인한 경우, 메인이 `harness/test-diff/approvals.toml`을 `master`의 단일 부모 직접 커밋으로 기록한다. 승인 파일을 변경하는 커밋에서는 승인 목록에 있는 테스트 파일을 함께 변경하지 않는다. 작업 브랜치에 적은 기록과 병합 커밋이 처음 도입하거나 변경한 기록은 승인 근거가 아니다. 브랜치의 원격 검사 전에 이 `master` 커밋을 받아야 한다. 새 판정기로 과거 `master` 트리를 평가할 때는 나중에 메인이 남긴 기록도 쓸 수 있지만, 검사 대상 커밋은 원격 `master`의 첫 부모 이력에 있어야 하고 그 커밋이 자신의 승인 기록을 도입해서는 안 된다. 과거 GitHub 실행의 일반 재실행은 그 커밋의 옛 판정기를 쓰므로 새 기록만으로 결과가 바뀌지 않는다. 얕은 저장소, 이력 확인 실패, 유효하지 않은 기록은 예외를 주지 않는다.

로컬 훅은 `origin/master` 추적 참조가 신뢰할 수 있는 fetch 결과라는 전제로 승인 이력을 읽는다. 이 참조를 임의로 바꾸면 로컬 판정은 위조할 수 있다. GitHub 체크아웃은 실제 원격 참조를 사용하고 병합 게이트는 원격 결과를 따로 검증한다. 최신 승인 커밋 직후의 `master` 병합에서는 승인 커밋과 테스트 변경이 같은 커밋이 아닌지 확인하고 그 승인을 사용한다.

이 권한은 메인이 원격 `master`를 관리하고 작업 브랜치를 `--no-ff`로 병합한다는 전제에 의존한다. 작업 브랜치의 승인 커밋과 테스트 커밋을 강제로 fast-forward해 원격 `master`에 먼저 올리면 Git 이력만으로 메인의 직접 승인과 구별할 수 없다. 그런 갱신을 승인 근거로 쓰지 않는다. 정상 로컬 검사와 푸시 검사는 갱신 전의 원격 추적 참조를 보므로 그 자기 승인을 거부한다.

승인 행마다 작업 ID, Rust 파일 경로, 해당 파일의 전·후 SHA-256, `test-diff`의 정확한 지적 문자열, `decision = "approved"`, 사유를 적는다. 파일의 실제 전·후 바이트와 그 파일에서 발생한 지적 집합이 승인 행과 정확히 같을 때만 `modified`와 함수·`impl`의 `support-modified`를 해소한다. 단언 문장이 바뀌는 지적 행에는 `assertion_change = true`와 비어 있지 않은 `reason`이 필요하다. 이 필드가 없는 기존 행은 단언이 같은 준비 변경에만 적용된다. 테스트 삭제, 단언 삭제, 미도달·목록 누락·개수 감소와 그 밖의 지적은 승인하지 않는다. 테스트 속성·서명과 단언 문장 수를 지키고, 승인된 단언 변경도 단언 호출의 종류·호출 대상, 내부 매크로와 단락 평가 구조가 같아야 한다. 자명한 참 단언, 단언 안의 새로운 제어 흐름과 준비 영역의 조기 반환·조건·반복은 거부한다. 지원 함수와 `impl` 안의 기존 메서드는 명시적으로 승인된 서명·준비 변경을 허용하며 기존 단언을 지켜야 한다. 이 구조 검사는 의미적 동등성이나 테스트 약화가 없음을 증명하지 않는다. 메인이 정확한 전·후 파일 차이와 승인 사유를 확인한다. 서명 검사의 `test-changes`에는 이 예외를 적용하지 않는다.

## 3. 기록

리뷰 지적, 비판 판정, 평가 결정은 `docs/reviews/<작업 ID>.md`에 남긴다. 기록할 항목:

| 항목 | 내용 |
|---|---|
| 브리프 | 브리프 전문 |
| 커밋 | 기준 SHA, 구현마다 대상 SHA |
| 구현 기록 | 회차별 실제 모델, 브리프 기준 SHA, 검사 대상 HEAD, 검사 종료 코드, 훅 적용 여부, "막힘" 여부와 이유. Claude 상태 기록과 Codex 결과를 혼동하지 않는다 |
| 리뷰 | 회차별 지적 목록 (등급, 재현 증거, 추정 여부) |
| 비판 | 지적별 판정과 증거, 고친 등급, 추가 지적 |
| 평가 | 지적별 결정과 이유, 기각을 뒤집은 경우 그 이유 |
| 측정 | 리뷰 등급, 리뷰 회차, 지적 수, 비판자의 기각률, 메인이 기각을 뒤집은 비율, 나중에 버그로 확인된 기각 건수(발견되면 해당 기록에 추가) |

- 반박 단계가 오탐을 얼마나 줄이는지는 정량 연구가 없다 (R-10 Q4). 위 측정 항목으로 이 저장소에서 직접 잰다.
- 새 기록의 `## 측정` 표에는 `리뷰 등급`과 실제 `리뷰 회차`를 각각 한 번 적는다. `## 커밋` 표의 실제 리뷰 회차와 측정 회차는 같고 등급을 넘지 않는다. 리뷰·비판은 회차마다 `## 리뷰 (회차 N)` 절을 순서대로 둔다. 마지막 회차 뒤 `N (… 수정)` 행은 별도 리뷰로 세지 않는다. 등급이 없는 과거 기록은 변경하지 않는다. 도입 전 기준 `d235aaf8d3f3a6387e0a20aede316cc5b7d0edbf`에 있던 기록이 같은 경로와 내용일 때만 등급 없는 기록으로 인정한다.
- 사용자가 독립 리뷰를 생략하기로 결정한 새 기록은 결정과 사유를 `## 리뷰 생략`에 적고 측정 표의 실제 리뷰 회차를 0으로 둔다. 이 경우 커밋 표의 행은 구현 이력이고 리뷰 절을 함께 두지 않는다.
- 기록 검사는 등급 값과 기록 내부의 회차 정합성을 확인한다. CI에는 메인이 작성한 브리프의 신뢰된 등급이 전달되지 않으므로 브리프에 지정한 등급을 기록에서 낮췄는지나 작업 위험도가 적절한지 기계적으로 증명하지 못한다. 메인은 브리프와 범위를 리뷰 기록에 대조한다.
- 기록 파일이 없는 작업은 완료로 표시할 수 없다. `just check`와 CI가 `docs/progress.md`에서 상태가 완료·일부 완료인 행마다 기록 파일이 있고 필수 절을 갖췄는지 검사한다. 메인 에이전트는 새 작업의 브리프를 쓰기 전에 `gh run list --branch master --limit 3`과 열린 'CI 실패' 이슈를 확인한다.
- 같은 종류의 지적이 두 번 나오면 하네스 규칙으로 만들 수 있는지 검토하고 tasks.md에 하네스 작업을 추가한다. 리뷰에서 반복해서 잡는 것은 하네스가 약하다는 뜻이다.

## 부록: 운영 규칙

역할과 Codex는 ADR 0021을 따르되, 2026-11-17 사용자 결정인 [H-50](adr/h-50-implementer-models.md)이 구현 모델·추론 강도·옵션 키 제한을 이 문서와 함께 대체한다. 제공자·격리·기준·소유권 규칙은 ADR 0021을 유지한다.

- 메인 Claude 세션은 원본 저장소에서 연다. Codex는 T3가 만든 등록된 작업 사본에서 연다. Codex의 프로젝트 설정과 훅 신뢰는 각각 확인한다.
- 구현·수정 회차는 T3 Codex `gpt-6.1-sol` 또는 `gpt-6.1-terra`(메인이 스레드를 띄울 때 정한다)가 한다. 기본 추론 강도는 sol은 high, terra는 max다. 조사·비판은 `gpt-6.1-sol`(high), 적대적 리뷰는 Claude Opus 5.5다. 브리프에는 `- 기준 커밋: <SHA>, 브랜치 \`<이름>\`` 줄이 반드시 있고, 그 브랜치는 `master`가 아닌 등록된 작업 사본이어야 한다.
- 수정 회차는 T3가 새 Codex에게 수정 브리프로 한다. 앞 단계의 브리프 기준 검사 성공이 확인되지 않았으면 기준은 `master` 끝이다.
- 구현자가 끝내려 하면 종료 훅이 `just base=<기준 SHA> check`를 네트워크가 막힌 채 돈다(3~5분). 작업 트리가 깨끗해야 한다.
- 병합 충돌은 구현자가 자기 브랜치에서 `git merge master`로 푼다. `rebase`는 쓰지 않는다.
- 기존 테스트를 바꿔야 하는 변경은 커밋 훅이 막는다. 사용자 서명 커밋으로만 들어간다.
- Claude Code를 업그레이드한 뒤에는 `just claude-regression`을 돌린다. "미확정"이 있으면 다시 돌리고, 실패면 결과 폴더(`target/claude-regression/`)와 `claude --version`을 기록한 뒤 하네스 작업으로 넘긴다.
- Codex를 올린 뒤 `just codex-regression`을 수동으로 돌린다. 구독 사용량을 쓰므로 `just check`에는 넣지 않는다. 알려진 빈틈은 `just known-gaps`로 본다.

## H-41 운영 규칙

- Claude SendMessage는 계속 금지한다. Codex 수정 회차는 T3의 소유 스레드 가드로 통제한다.
- 메인은 이 프로젝트의 T3 문맥에서 t3_thread_launch로 구현을 시작한다. modelSelection은 provider=codex, model은 정확히 gpt-6.1-sol 또는 gpt-6.1-terra다. sol의 운영 기본 요청은 reasoningEffort=high다. 기존 호환을 위해 options 생략·빈 객체·빈 배열도 허용하므로 이 경로의 실제 강도는 T3의 상속·기본값에 따르고 high를 보장하지 않는다. Terra options는 reasoningEffort=max를 명시하며 생략·빈 객체·빈 배열은 거부한다. 기존 effort 키도 같은 값만 허용하며 두 키를 섞지 않는다. Terra 시작 브리프에는 정확히 한 개의 `- 역할: implementation` 줄을 넣는다. 정확히 이 형식인 줄만 역할 선언으로 센다. 인식된 선언이 없거나 중복되거나 implementation이 아니면 Terra를 거부한다. 다른 들여쓰기·목록 표기와 코드 펜스에 역할을 쓰지 않는다. 가드는 본문 의미와 코드 펜스를 해석하지 않는다. 조사·비판은 delegate_task의 research·review 역할로 sol에 맡긴다. workspaceStrategy는 type=worktree, branch=브리프 브랜치, 로컬은 baseRef=브리프 SHA·startFromOrigin=false다. 원격은 baseRef=origin/master·startFromOrigin=true이며 브리프 SHA는 그 원격 추적 끝과 같아야 한다.
- projectId·environmentId·scratch·다른 제공자·권한 확대는 넘기지 않는다. 현재 프로젝트와 환경을 상속한다. runtimeMode는 생략 또는 approval-required다.
- 실행 결과의 threadId를 메인 세션 소유 기록에 저장한다. 그 기록과 등록된 worktree가 있는 스레드만 t3_thread_read·t3_thread_wait·t3_thread_send로 접근한다. 허용 인자 밖은 거부한다.
- 수정은 같은 스레드의 t3_thread_send(mode=auto 또는 생략)로 계속할 수 있다. 수정 브리프는 기준 SHA와 기존 브랜치를 포함한다. SHA는 master 끝의 자손이며 해당 작업 사본 HEAD의 조상이어야 한다. 메인이 앞 구현의 전체 검사와 리뷰 판정을 확인한다. Claude의 passedTargets가 없어도 같은 스레드 수정은 가능하다.
- 적대적 리뷰어는 매번 새 Claude Opus 5.5다. 구현자 보고를 넘기지 않고 격리·오염 감지를 그대로 적용한다.
- 새 가드 적용 전에 시작된 스레드는 소유 기록이 없다. 자동으로 외부 스레드를 채택하지 않는다. 메인은 새 가드로 시작한 스레드부터 이 절차를 적용한다.
- 구현 담당은 docs/progress.md를 편집하지 않는다. 진행 상태는 보고서에 쓰고 메인이 한 줄 메모나 완료 행을 반영한다.

T3 도구는 전체 matcher에서 기본 거부한다. 허용된 launch·send·read·wait와 project_list·orchestrator_capabilities·background_wait만 쓴다. configure·queue 편집으로 모델이나 브리프를 바꾸지 않는다. 하네스 프로필 삭제와 잠금 전 prelock 절차는 ADR 0021 B를 따른다.

## H-51 로컬 전체 정리

`fresh-cargo`와 `fresh-build`는 workspace 산출물을 정리한다. 외부 의존성까지 지운 전체 빌드를 수동으로 확인하려면 `just fresh-all` 다음에 `just base=HEAD check`를 실행한다. 전체 정리는 `target/` 아래 기록도 지우므로 중요한 로컬 자료는 밖에 둔다. 메인 빌드 산출물 복제는 실측 개선 기준을 충족하지 못해 사용하지 않는다.
