# 작업 절차 (v0.2)

모든 구현 작업은 이 절차를 따른다. 예외는 없다. 절차를 강제하는 훅과 설정은 [harness.md](harness.md) 7장에 있다.

## 1. 역할

| 역할 | 누가 | 하는 일 | 강제 |
|---|---|---|---|
| 메인 에이전트 | 사용자와 대화하는 세션 | 작업 선정, 브리프 작성, 평가, 수정 여부 판단, 리뷰 기록, 푸시, 사용자 보고. 코드를 직접 쓰지 않는다 | 편집 훅이 메인에게 `docs/**`(보호 문서 제외)만 허용 |
| 구현 에이전트 | 새 Opus 5.5 서브에이전트 (`implementer`) | 작업 하나를 구현하고 `just check`를 통과시킨다 | 종료 훅이 `just check`를 돌린다 |
| 적대적 리뷰어 | 새 Opus 5.5 서브에이전트 (`adversarial-reviewer`) | 구현을 깨뜨릴 방법을 찾고 등급을 매긴다. 판정하지 않는다 | 편집 도구 없음, 격리된 작업 사본, 원본 변경 감지 훅 |
| 비판자 | 새 Opus 5.5 서브에이전트 (`review-critic`) | 리뷰 지적을 하나씩 실행으로 반박해 본다 | 리뷰어와 같음 |

"새"는 앞 단계의 대화 맥락을 물려받지 않는다는 뜻이다. 각 서브에이전트는 자기 정의, 메인의 위임 메시지, 저장소만 본다. 포크와 `SendMessage`(끝난 서브에이전트 재개)는 금지되어 있다. 모델은 정의 파일의 `claude-opus-5-5`이고, 호출할 때 `model` 인자를 넘기면 훅이 거부한다.

## 2. 순서

```
1. 브리프      메인이 작업 단위 하나를 골라 브리프를 쓴다
2. 구현        implementer가 구현하고 just check를 통과시킨다 (또는 "막힘")
3. 적대적 리뷰  adversarial-reviewer가 지적 목록을 만든다
4. 비판        review-critic이 지적마다 확정·기각·불확실을 판정한다
5. 평가        메인이 지적별로 수정·보류·기각을 결정한다
6. 수정        새 implementer가 수정한다. 차단·중요 등급을 고쳤으면 3으로 돌아간다
7. 완료        메인이 리뷰 기록과 tasks.md를 갱신하고 푸시한 뒤 사용자에게 보고한다
```

- 푸시는 메인 에이전트만 한다. 서브에이전트는 푸시하지 않는다. CI의 서명 검사는 푸시 뒤에 도는 사후 탐지다 ([harness.md](harness.md) 7.6).

### 2.1 브리프

메인 에이전트는 새 작업의 브리프를 쓰기 전에 `main`의 CI가 통과 상태인지 확인한다. 실패면 멈추고 사용자에게 보고한다. CI가 아직 없으면(H-16 이전) 이 확인은 건너뛴다.

메인 에이전트가 쓴다. 양식:

```markdown
# 브리프 <작업 ID> <제목>
- 기준 커밋: <SHA>
- 완료 기준 (tasks.md 그대로. 각 기준은 통과·실패로 판정할 수 있어야 한다)
  1. ...
- 관련 요구사항: SEC-.., ORD-..   관련 구조 규칙: architecture.md x.y
- 손댈 범위: crates/<name>/src/**, crates/<name>/tests/**
- 손대면 안 되는 범위: (보호 경로 외에 추가로)
- 정해진 결정: ADR-NNNN
- 검사 명령: just check
- 막혔을 때: 보고서 첫 줄을 "막힘:"으로 시작하고 멈춘다
```

| 항목 | 이유 |
|---|---|
| 기준 커밋 SHA | 리뷰어와 비판자가 같은 기준으로 `git diff`를 만든다. 테스트 변경 검사(`xtask test-diff`)의 기준이기도 하다 |
| 통과·실패로 판정할 수 있는 완료 기준 | 검사로 돌아오는 기준이 있어야 증거를 낼 수 있다 |
| 검사 명령 | 증거로 낼 명령을 정해 둔다 |
| "막힘:" 출구 | 억지로 통과시키는 대신 멈출 수 있는 정상 출구다. 사람에게 넘기는 출구를 주면 편법이 줄었다는 연구가 있다 (R-10 Q6) |

- 브리프에 구현 방법을 지시하지 않는다. 무엇이 참이어야 하는지만 쓴다.
- 작업 크기: 완료 기준 3~5개, crate나 기능 폴더 하나에 들어가는 크기. 이것은 리서치의 1차 근거가 아니라 판단이다 (R-10 Q8).

### 2.2 구현

- 작업 하나에 브랜치 하나, 커밋은 작게. 구현 에이전트는 푸시하지 않고 서명 옵션을 쓰지 않는다.
- `just check`가 통과해야 끝난 것이다. 통과시키기 위해 검사를 끄거나 테스트를 지우거나 약하게 만들지 않는다. 기존 테스트의 삭제·변경은 `xtask test-diff`가 실패시킨다.
- 하네스가 막으면 우회하지 않고 멈춘 뒤 "막힘:"으로 보고한다 ([harness.md](harness.md) 8장).
- 종료하려 하면 훅이 `just check`를 돌린다. 실패하면 실패 출력이 돌아온다. 3번 막힌 뒤에는 "막힘:" 보고와 함께 종료가 허용된다.
- 보고 형식: 첫 줄 "완료" 또는 "막힘: <한 줄 이유>", 커밋 SHA와 바꾼 파일, 완료 기준별 충족 근거(테스트 이름, 명령과 출력), `just check` 마지막 요약 줄, 확신이 없는 부분과 범위 밖에서 발견한 문제.

구현이 끝나면 메인이 확인한다:

| 확인 | 기준 |
|---|---|
| 하네스 기록 | `PostToolUse(Agent)`가 붙인 상태가 `passed`인가. `failing`, `blocked`, `unchecked`이면 완료가 아니다 |
| 실제 모델 | 기록된 `resolvedModel`이 Opus 5.5인가 |
| 범위 | 대상 커밋의 변경 파일이 브리프의 "손댈 범위" 안에 있는가 |
| 작업 사본 | `git status`에 커밋되지 않은 파일, 특히 보호 대상이 될 새 파일이 없는가 |
| 막힘 | "막힘:"이면 2.7로 간다 |

### 2.3 적대적 리뷰

리뷰어에게 주는 것:

| 준다 | 주지 않는다 |
|---|---|
| 브리프, 기준 커밋 SHA, 대상 커밋 SHA | 구현 에이전트의 보고서 |
| 저장소 | 메인이 요약한 변경 차이 |

- 리뷰어는 격리된 작업 사본에서 `git checkout --detach <대상 SHA>`를 한 뒤 `git diff <기준 SHA>...HEAD`로 변경을 직접 본다. 메인의 요약도 편향이 되므로 주지 않는다.
- 구현자의 설명을 주지 않는 이유: PR 설명을 다듬어 보안 판정을 바꾸는 공격이 Claude Code 리뷰 파이프라인에서 33건 중 32건 성공했다는 연구가 있다 (R-10 Q4).
- 재현용 파일은 작업 사본 안에만 만든다. 원본이 바뀌면 종료 훅이 막는다.

리뷰어의 목표는 승인이 아니라 결함을 찾는 것이다. **리뷰어는 판정하지 않고 등급만 매긴다.** "큰 문제가 아니다"라고 스스로 설득해 승인하는 실패를 구조로 막기 위해서다. 확인할 것:

- 완료 기준을 실제로 충족하는가. 테스트가 기준을 정말 검증하는가
- 잘못된 입력, 경계값, 순서 바뀜, 동시 실행, 부분 실패, 재시도에서 깨지는가
- 주문·금액·비밀 값과 닿는 변경이면 design.md의 SEC, ORD, ACC 항목을 어기는가
- 구조 규칙을 문자 그대로는 지키면서 취지를 어기는가
- 기존 테스트의 삭제·약화, 건너뛰기
- 새로 생긴 검사 끄기마다 규칙을 지키는 다른 방법이 없었는가 ([harness.md](harness.md) 2.1). 끄기 목록을 리뷰 기록에 적는다
- [harness.md](harness.md) 9장 "리뷰에서 확인할 항목" 중 이 변경에 해당하는 것 전부

등급:

| 등급 | 기준 |
|---|---|
| 차단 | 완료 기준 미충족, SEC/ORD/ACC 위반, 데이터 손상 가능, 검사 우회나 테스트 약화 |
| 중요 | 특정 입력·순서·동시성에서 틀린 결과나 오류 누락 |
| 사소 | 동작은 맞지만 다음 변경에서 결함을 부르기 쉬운 것 |

지적 형식: 번호, 등급, 파일과 줄, 재현 명령과 실제 출력(또는 반례 입력과 기대값·실제값), 근거(위반한 기준이나 문서 위치), "추정" 여부. 재현하지 못한 지적은 "추정"으로 표시하고 재현에 필요한 것을 쓴다. 형식, 이름, 취향, 린터가 잡는 것, 변경 전부터 있던 문제는 지적하지 않는다.

리뷰가 끝나면 메인은 원본 작업 사본의 `git status`와 HEAD가 리뷰 전과 같은지 확인한다. 다르면 다음 단계로 가지 않고 사용자에게 보고한다.

### 2.4 비판

비판자에게 주는 것: 브리프, 기준·대상 커밋 SHA, 리뷰 지적 목록, 저장소. 구현자의 보고서는 주지 않는다.

비판자는 토론하지 않고 실행으로 검증한다. 지적마다 먼저 반박을 시도하고, 반박이 안 되면 직접 재현한다.

- **확정**: 재현했거나 코드로 확인했다. 명령과 출력, 또는 파일과 줄을 붙인다
- **기각**: 지적이 틀렸다. 반례 실행 결과나 파일과 줄을 붙인다. 근거 없는 기각은 하지 않는다
- **불확실**: 판정하려면 무엇이 더 필요한지 쓴다

등급이 결과와 맞지 않으면 고친 등급과 이유를 쓴다. 비판자는 리뷰어가 놓친 것을 발견하면 같은 형식의 추가 지적으로 덧붙인다.

### 2.5 평가

메인 에이전트가 한다. 지적별로 결정한다.

| 결정 | 조건 |
|---|---|
| 수정 | 확정된 차단·중요 등급. 확정된 사소 등급 중 고치는 비용이 작은 것 |
| 보류 | 확정됐지만 이 작업 범위 밖인 중요·사소 등급. tasks.md에 새 작업으로 추가한다. 차단 등급은 보류할 수 없다 |
| 기각 | 비판자가 근거를 붙여 기각했고 메인도 그 근거를 확인했다 |
| 추가 확인 | 불확실. 차단 등급이면 사용자에게 보고한다. 그 외는 메인이 명령을 돌려 직접 확인한다 |

- 리뷰어와 비판자의 등급이 다르면 재검토 여부는 높은 쪽 등급으로 정한다.
- 메인은 완료 기준 충족 여부를 지적과 별개로 다시 판단한다. 지적이 0건이어도 기준 미충족이면 반려한다.
- 메인이 비판자의 기각을 뒤집으면 이유를 기록한다 (3장 측정 항목).

### 2.6 수정과 재검토

- 수정은 새 `implementer`가 한다. `SendMessage`가 금지되어 있어 앞의 구현자를 이어 쓸 수 없다.
- 수정 브리프에는 원래 브리프, 새 기준 커밋(앞 단계의 대상 SHA), 평가 결과, 고칠 지적을 넣는다.
- 차단이나 중요 등급을 고쳤으면 3단계부터 다시 한다. 리뷰어와 비판자도 새로 띄운다.
- 사소 등급만 고쳤으면 메인이 차이와 하네스 기록을 확인하고 끝낸다.
- 같은 작업에서 리뷰를 3번 돌려도 차단 등급이 남으면 멈추고 사용자에게 보고한다. 작업을 더 쪼개야 한다는 신호다.

### 2.7 "막힘" 처리

구현 에이전트가 "막힘:"으로 끝나면 메인은 이유를 보고 하나를 고른다.

| 이유 | 처리 |
|---|---|
| 작업이 너무 크거나 완료 기준이 서로 모순됨 | 작업을 쪼개거나 기준을 고쳐 새 브리프로 다시 시작한다. 완료 기준을 고치면 사용자에게 알린다 |
| 하네스 규칙이 정상 구현을 막음 | [harness.md](harness.md) 8장. 사용자에게 보고하고, 사람이 규칙을 바꾸기로 하면 ADR과 서명 커밋으로 바꾼다 |
| 기존 테스트가 틀렸다고 판단함 | 사용자에게 보고한다. 기존 테스트 변경은 사용자 서명 커밋으로만 들어간다 |
| `just check`를 3번 연속 통과하지 못함 | 실패 출력을 보고 새 브리프를 쓰거나 사용자에게 보고한다 |
| 하네스 기록이 `unchecked` (종료 훅이 검사하지 못함) | 메인이 `just check`를 직접 돌려 상태를 확인한 뒤 판단한다 |

## 3. 기록

리뷰 지적, 비판 판정, 평가 결정은 `docs/reviews/<작업 ID>.md`에 남긴다. 기록할 항목:

| 항목 | 내용 |
|---|---|
| 브리프 | 브리프 전문 |
| 커밋 | 기준 SHA, 구현마다 대상 SHA |
| 구현 기록 | 회차별 하네스 상태(`passed`, `failing`, `blocked`, `unchecked`), `resolvedModel`, "막힘" 여부와 이유 |
| 리뷰 | 회차별 지적 목록 (등급, 재현 증거, 추정 여부) |
| 비판 | 지적별 판정과 증거, 고친 등급, 추가 지적 |
| 평가 | 지적별 결정과 이유, 기각을 뒤집은 경우 그 이유 |
| 측정 | 리뷰 회차, 지적 수, 비판자의 기각률, 메인이 기각을 뒤집은 비율, 나중에 버그로 확인된 기각 건수(발견되면 해당 기록에 추가) |

- 반박 단계가 오탐을 얼마나 줄이는지는 정량 연구가 없다 (R-10 Q4). 위 측정 항목으로 이 저장소에서 직접 잰다.
- 기록 파일이 없는 작업은 완료로 표시할 수 없다. CI가 tasks.md에서 완료로 표시된 작업마다 기록 파일이 있는지 검사한다.
- 같은 종류의 지적이 두 번 나오면 하네스 규칙으로 만들 수 있는지 검토하고 tasks.md에 하네스 작업을 추가한다. 리뷰에서 반복해서 잡는 것은 하네스가 약하다는 뜻이다.

## 4. 사용자가 직접 하는 일

| 일 | 이유 |
|---|---|
| 토스 키 발급, 허용 IP 등록, 실제 키로 도는 검증 스크립트 실행 | 에이전트는 키를 다루지 않는다 |
| 실제 주문이 나가는 검증 | 돈이 움직인다 |
