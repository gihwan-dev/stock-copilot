## 1. 적대적 리뷰 지적

### 차단

| # | 위치 | 지적 |
|---|---|---|
| 1 | architecture 3.4, 4.1 / tasks D-14, O-03, S-07 | `ApprovalToken`과 `Proposal<State>`가 `domain`에 있는데 생성자는 `application` 승인 모듈에서만 보여야 한다고 한다. Rust 가시성으로는 다른 crate의 특정 모듈에만 열 수 없어 `pub`이 된다. 제안을 SQLite에서 복원하면 `store-sqlite`가 `Proposal<Approved>`를 만들 수 있다. `UserApproval`을 누가 만드는지 정의가 없다 |
| 2 | architecture 3.2, 4.2 / AGENTS 6 | 주문 경로 차단이 `mcp-server` 소스의 이름 검색뿐이다. 타입 별칭, `ApproveProposal`·`SubmitOrder` 유스케이스 직접 호출, `BrokerTrade`를 든 서비스 주입, `src-tauri`의 클로저 등록으로 우회된다. `scheduler`와 `ai-*`는 검사 대상이 아니다. `xtask`가 의존 표에 없는데 T-12에서 `broker-toss`를 쓴다. 테스트용 생성자를 feature로 열면 우회된다 |
| 3 | design 6장, SEC-5, SEC-8 / tasks C-05, U-03 | 승인은 WebView가 부르는 IPC 명령이라 코어가 버튼 클릭과 JS 호출을 구분하지 못한다. AI 마크다운이 같은 WebView에 렌더링되므로 XSS 하나가 무승인 주문이 된다. Touch ID는 5분 미사용 뒤에만 요구한다. "수정 후 승인"의 재검증 정의가 없다 |
| 4 | design ORD-2 / tasks O-04, T-16 | 스펙상 `Order` 조회 응답에 `clientOrderId`가 없고 거래내역은 주문 식별자를 주지 않는다. `clientOrderId` 멱등성은 10분간 유효하고 같은 값 재요청은 이전 결과를 돌려준다. "재전송 금지, 조회로 확인"은 스펙대로는 불가능하고, 스펙이 의도한 복구(같은 키 재전송)를 설계가 금지한다 |
| 5 | tasks H절 머리말 / harness 7.1 | "H-12 뒤 잠금"인데 H-13~H-18, T-12, DS-02가 보호 파일을 쓴다. 잠금 수단(H-15 훅)이 잠금 시점보다 뒤에 만들어진다 |
| 6 | harness 7.1, 7.2 | 편집 도구만 차단해 Bash(`sed -i`, `cat >`)로 우회된다. 보호 목록 밖의 끄는 지점: `.cargo/config.toml` rustflags, crate `Cargo.toml`에서 `lints.workspace = true` 제거, `package.json` scripts, vitest·knip·mutants 설정, `lefthook-local.yml`, `LEFTHOOK=0`, `core.hooksPath`, `CLAUDE.md`, 심볼릭 링크. CI의 "사람 승인 표시"를 에이전트가 커밋 메시지에 쓸 수 있다 |
| 7 | harness 7.2, 8장 / workflow 2.2 | Stop 훅(검사 실패 시 종료 차단)과 "막히면 멈추고 보고"가 충돌한다. 서브에이전트 종료는 `SubagentStop` 이벤트라 implementer에게 Stop 훅이 걸리지 않는다(추정) |
